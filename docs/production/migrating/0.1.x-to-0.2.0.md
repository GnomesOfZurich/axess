# 0.1.x to 0.2.0

0.2.0 is the first release published to crates.io. Every change since
the previous stable line is listed in
[`CHANGELOG.md`](https://github.com/GnomesOfZurich/axess/blob/main/CHANGELOG.md);
this chapter covers the breaking ones an adopter has to act on.

### Compile errors you will see

`use axess::PolicyStore` becomes `use axess::AuthzStore`. The
authorisation entry point now follows the `Authz*` prefix convention,
and the new name says what the type is: an immutable store of policies
plus schema, not just a policy collection.

`use axess::AxessSession` becomes `use axess::AuthSession`. The
session extractor now uses the shared `Auth*` prefix from the naming
conventions (*Architecture at a glance*).

`use axess::backends::SqliteStore` becomes
`use axess::backends::sqlite::SessionStore`. The reorganised
backend modules use the same name (`SessionStore`) under each backend's
namespace. The flat `SqliteStore` symbol no longer exists.

`AuthnService::new(backend)` becomes
`AuthnService::new(identity_store, factor_store)`. The service
now takes the two stores separately so adopters can wire
different implementations (for instance, a read-replica
identity store and a write-only factor store). When the two
stores are the same type (the common case), pass it twice.

The signing key is a constructor argument, not a builder call:
`SessionLayer::new(store, signing_key)`, taking `[u8; 32]`. Rotation
is the one related builder, `with_previous_signing_key`, which keeps
the outgoing key valid for verification while the new one signs.

`AuthState::Logged` becomes `AuthState::Authenticated`. The
variant was renamed for clarity; nothing else about it changed.

### Configuration changes

The `axess_factors_default_password_hasher` config function is
gone. Argon2id is now the default; deployments that need a
different hasher (PBKDF2, legacy bcrypt) implement a custom
factor and register it. *Factors and methods* covers the
extension pattern.

There is no audit-pipeline config type to migrate: axess awaits one
call, `IdentityAuthnLog::record_event`, and the implementation behind
it is yours; a deployment that had wired sinks into a config struct
wires them inside that implementation instead. *Audit pipeline* covers
the seam.

`RateLimitConfig` has no `key_fn` field and no custom extractor:
the bucket key is a `KeyExtractor` in the `key_extractor` field
(the builder's `key`), one of `ForwardedIp`, `PeerIp`, `UserId`,
`TenantId`, `LoginIdentifier` and `Header(String)`, the last
keying on the value of a named header.

### Behaviour changes

The `Authenticating` state now carries a `Vec<FactorKind>` for
`remaining` rather than the previous `Option<FactorKind>`. The
change enables multi-factor methods with more than two factors. Code
that pattern-matched on `Some(kind)` must match on `remaining.first()`
or iterate over the list.

`LockoutPolicy` is per-user and has no other scale. It is three
fields (`max_attempts`, `duration`, `attempt_window`) with no
per-tenant or per-IP variant to configure or to turn off. Throttling a
source IP is the rate limiter's job, where the answer is a 429 rather
than a locked account; see *Rate limiting*, and note
`KeyExtractor::LoginIdentifier` for the per-account half of that
defence.

The session cookie's `SameSite` attribute now defaults to `Lax`
rather than `Strict`. `Lax` matches modern browser
defaults and admits cross-site link-to-app navigations as
legitimate. Deployments that need `Strict` configure it
explicitly.

Session binding is off unless you ask for it. Nothing is bound until
the layer is built with `.with_binding(UserAgentBinding)`, and a mismatch
then resets the session to `Guest`. There is no policy to set and no
quieter setting to start from (*Cookies, fingerprinting, hijack
detection* covers the limits of what the binding catches).

### Schema migrations

No table needs a migration. 0.2.0 is the first release whose source is
published, and its one schema file,
`examples/sqlite/migrations/20250523163859_schema.sql`, creates every table
(`tenants`, `users`, `factor_configs`, `auth_methods`, `auth_events`,
`sessions`, `password_history`, `password_reset_tokens`, `refresh_tokens`)
and alters none. The SQL device stores create their own `devices` table,
with its `fingerprint_hash` column, in `init_schema`.

The session-data schema version is 2. Version 2 added
`device_id: Option<DeviceId>` to `SessionData` (for the device-binding work
covered in *Device identity*). A version-1 session reads with `device_id`
set to `None`, and the schema-migration code (*Schema migration*) bumps its
version when it is saved again; no manual data migration is needed.

### Workspace structure changes

The `axess-delegated` crate folded back into `axess-core`. Import
paths stay the same: `axess::delegated::*` still works through the
facade re-export. Your `Cargo.toml` no longer needs an explicit
`axess-delegated` dependency, only the `delegated` feature on `axess`. The
workspace dropped from 11 to 10 library crates.

### Recommended migration sequence

For deployments running on the 0.1.x line:

First, read this chapter end to end and list every change that applies
to your code.

Second, deploy in parallel: stand up a 0.2.0 build alongside the
production 0.1.x, route a small fraction of traffic to it, and observe
its behaviour. Session cookies are not compatible between the two
versions (0.2.0 upgrades a session stored under an earlier schema
version when it loads it, but never converts one back), so
the parallel deploy needs isolated session storage.

Third, cut over. Once the 0.2.0 build has been green for at least the
session TTL on the production-like sample, route 100% of traffic to it.
Decommission the 0.1.x build once a roll-back window passes without
incident.

To roll back if 0.2.0 surfaces problems, route traffic back to 0.1.x.
Sessions that started under 0.2.0 are invalid against 0.1.x and land as
`Guest`, so those users sign in again. The impact is bounded to that one
re-login.
