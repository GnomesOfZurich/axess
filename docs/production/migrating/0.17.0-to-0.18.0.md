# 0.17.0 to 0.18.0

Compile breaks first: the compiler finds each of them for you. Then the
behaviour changes, which it does not, and last what is new and breaks
nothing.

### Compile breaks

- **`PolicyStore::digest()` returns `String` and `PolicyStore::schema()`
  returns `Schema`, "expected `&str`", "expected `&Schema`".** Both follow a
  reload, so they return values instead of borrows from the object. Change
  `Some(store.schema())` to `Some(&store.schema())`, and compare a digest with
  `store.digest() == other` (a `String`). `original_digest()` and
  `original_schema()` return the borrowed values of the text the object was
  built from, whatever was reloaded since.

- **`webauthn-rs` is 0.6.2, and `CredentialID` is `Vec<u8>`: "cannot find
  `Base64UrlSafeData` in `webauthn_rs::prelude`", "expected
  `HumanBinaryData`, found `Vec<u8>`".** axess now depends on the 0.6.2
  release (`^0.6.2`) instead of the `=0.6.0-dev` pre-release; an application
  that names `webauthn-rs` itself moves to 0.6.2 with it. `CredentialID`,
  re-exported from `axess_factors::fido2`, was `HumanBinaryData` and is now a
  plain `Vec<u8>`: use it as one (`.as_slice()` where an `.as_ref()` no
  longer infers its target), and build one with `vec![..]` or `Vec::from(..)`.
  The prelude no longer exports `Base64UrlSafeData`. Stored passkeys and
  in-flight ceremony state keep their JSON form (URL-safe base64 without
  padding) and read back unchanged. Upstream deprecated
  `Webauthn::finish_discoverable_authentication`; `DefaultFido2Provider` now
  verifies with the single-credential method, and the `Fido2Provider` trait
  is unchanged.

- **`PolicyEvaluator::schema` returns `Option<Schema>`, "method `schema` has an
  incompatible type for trait".** The schema is returned by value so it can
  follow a reload. An evaluator of your own that overrode the borrowing
  method changes `fn schema(&self) -> Option<&Schema>` to
  `fn schema(&self) -> Option<Schema>` and returns a clone (`Some(self.schema.clone())`);
  one that never overrode it needs nothing.

- **`DisplacedSid` has a new field: "missing field `tenant` in initializer".**
  The mapping a login displaced now carries the tenant it was recorded for.
  Add `tenant: None` where you build one by hand (a test, say); the login
  path fills it.

- **`SidMap::insert`, `insert_displacing` and `register_subject_session` take
  a tenant: "this method takes 6 arguments but 5 arguments were supplied".**
  The third argument is `tenant: Option<TenantId>`: the tenant of the
  provider the user logged in through, `None` for a global provider's login.
  The tenant-less forms are gone, so a record cannot be made that a tenant
  provider's logout never finds. The compiler lists the call sites.

- **`LogoutTokenClaims` has a new field `tenant`**, the tenant whose
  provider verified the token (`None` for a global provider). Code that
  builds one by hand adds `tenant: None`.

- **`DelegatedCredentialStore::save_if_unchanged` has no default: "not all trait items implemented, missing: `save_if_unchanged`".**
  A refresh writes its result with it, so a row removed or replaced while the
  IdP was being asked is not written back, in this process or another. Implement
  it atomically. For a SQL store it is one conditional update, returning
  `Saved` when a row changed and `Changed` when none did:

  ```sql
  UPDATE delegated_credentials
     SET access_token = ?, refresh_token = ?, expires_at = ?, scopes = ?, token_type = ?
   WHERE tenant_id = ? AND user_id = ? AND provider = ?
     AND access_token = ? AND refresh_token IS ? AND expires_at IS ?
  ```

  (the last three compare the columns of `expected`). A store that cannot do
  it says so, in one line, and keeps the old behaviour (the refresh falls back
  to the unconditional `save`, with a warning naming the store type once, and a
  revoke made in another process during a refresh is overwritten):

  ```rust,ignore
  async fn save_if_unchanged(&self, _: &TenantId, _: &UserId, _: &StoredDelegation, _: StoredDelegation)
      -> Result<CredentialSwap, String> { Ok(CredentialSwap::Unsupported) }
  ```

  `EncryptedDelegatedCredentialStore` implements it over the sealed rows,
  atomic exactly when the inner store's is; over an inner store that answers
  `Unsupported` the result is `Unsupported`.

- **`IdentityPasswordReset::store_reset_token` has a new signature: "method
  `store_reset_token` has 5 parameters but the declaration in trait has 3".**
  A new request must not replace a live token, so the store now keeps several:
  `store_reset_token(user_id, token_hash, expires_at, now, max_live)` returns
  `Ok(true)` when it stored the token and `Ok(false)` when the user already
  holds `max_live` live ones (live means `expires_at > now`; remove the user's
  expired tokens in the same step; storing a hash already held is `Ok(true)`).
  `verify_reset_token` and `check_reset_token` compare against every live token
  of the user, and a successful `verify_reset_token` deletes all of them. The
  count, the cleanup and the insert are one atomic step. With SQL, make the key
  `(user_id, token_hash)` instead of `user_id`:

  ```sql
  CREATE TABLE password_reset_tokens (
      user_id TEXT NOT NULL, token_hash TEXT NOT NULL, expires_at TEXT NOT NULL,
      PRIMARY KEY (user_id, token_hash)
  );
  ```

- **`IdentityAdmin::delete_candidates_created_before` is a new required
  method: "not all trait items implemented".** It deletes up to `limit` users
  that are still `Candidate` and were created before `before`, as
  `delete_user` erases them, and returns the users deleted. Nothing in another
  state is touched.

- **`TenantOAuthProviders::built_providers` is a new required method.** Return
  the providers the registry holds built, so the JWKS refresh covers them. A
  registry that holds none says so on purpose:

  ```rust,ignore
  fn built_providers(&self) -> Vec<Arc<dyn OAuthProvider>> {
      Vec::new()
  }
  ```

- **`OidcError` has a new variant `EgressRefused { setting, range }`:
  "non-exhaustive patterns".** An `EgressPolicy` refused the issuer URL or an
  endpoint its document names. It carries the setting and the reason, never the
  URL or an address. Add an arm.

- **`DeviceResolver::resolve` returns `Option<BoundDevice>` instead of
  `Option<DeviceId>`.** A lockout exemption now accepts only a device the
  client proved, so the resolver says which it found. A resolver that finds a
  device by any means but the secret cookie token returns the id with
  `.into()` (`BoundDevice::Unproven`): the session keeps it as a label and the
  exemption ignores it. Only a resolution by `resolve_proven` yields
  `BoundDevice::Proven` (`BoundDevice::Proven(resolved.proven())`).
  `SessionData` has a new field `device_proven`; a literal of it needs
  `device_proven: false`. A session stored before the field existed reads
  unproven until its next request resolves the device again. `ResolvedDevice`
  can no longer be built by a struct literal.

- **`SocialClaims` has a new field: "missing field `email_verified` in
  initializer of `SocialClaims`".** The claim mapper of a `SocialProvider` now
  says whether the provider verified the address it returns, so a mapper cannot
  hand over a profile address that looks verified. There is no default. Set it
  per provider, and link or create accounts by `email` only when it is `true`:

  ```rust,ignore
  Ok(SocialClaims {
      subject: id.to_string(),
      // GitHub's profile address carries no verified flag.
      email: None,
      email_verified: false,
      display_name: raw.get("name").and_then(|v| v.as_str()).map(String::from),
      raw: raw.clone(),
  })
  ```

  A provider that states it (Discord's `verified`, an OIDC `email_verified`)
  maps that flag; when in doubt, `false`.

- **`Fido2Provider`'s ceremony methods take the ceremony and typed state,
  "method `start_authentication` has 2 parameters but the declaration in
  trait has 3".** `start_registration` and `start_authentication` take a
  `&Fido2Ceremony` first; `start_authentication` takes `&[Fido2Key]` instead
  of `&[Passkey]`; the state is `Fido2Registration` / `Fido2Authentication`
  instead of `PasskeyRegistration` / `PasskeyAuthentication`; and
  `finish_registration` returns a `Fido2Key`. A provider that wraps
  `DefaultFido2Provider` forwards the new arguments; one of your own matches
  on the ceremony (`Fido2Ceremony::Passkey` is what 0.17 ran). The new
  `attests` method defaults to `None`. See
  [Authentication assurance and ceremonies](../../authorization/assurance.md).

- **`Fido2Credential::passkey` is `Fido2Credential::key: Fido2Key`, "no field
  `passkey`".** A credential keeps the type of the ceremony that registered
  it. `Fido2Credential::new` takes anything that converts into a `Fido2Key`,
  so `Fido2Credential::new(passkey, name, at)` still compiles; read the
  passkey with `credential.key.passkey()` and the id with `cred_id()`. A
  stored passkey row reads unchanged, and a passkey is still written in the
  form 0.17 reads.

- **`Fido2Options` has `registration_ceremony` and `login_ceremony`, "missing
  fields".** A struct literal adds them or ends with
  `..Fido2Options::default()`; both default to `DEFAULT_FIDO2_CEREMONY`, the
  passkey ceremony.

- **`AuthState::Authenticating` and `AuthState::Authenticated` have an
  `assurance` field, and `StandardRequestContext` has `assurance`, "missing
  field `assurance`".** A struct literal adds `assurance: Vec::new()` (or
  `assurance: None` for the context); a pattern adds `..`. Build the context
  with `StandardRequestContext::new` or `at`, and add the record with
  `with_assurance`.

- **`PolicyEvaluator` has a defaulted `step_up_for`.** Nothing to change for
  an evaluator of your own; it names no step-up unless it overrides the
  method.

### Behaviour changes

- **A policy reload now reaches `require_authz!` gates.** In 0.17.0 the gate
  read the `Arc<PolicyStore>` from the request extensions and that object
  never saw a reload, so a tightened policy answered 200 on every gated route
  while `reload_policies` returned `Ok`. `reload_policies` now points the
  `PolicyStore` the `AuthzStore` was built with at the new set, and a decision
  on that object, from the gate or the store, uses it with one atomic load.
  The wiring stays as it was: one `Arc<PolicyStore>`, installed as the
  extension and handed to `AuthzStore::try_new`. A gate wired with a
  *different* `PolicyStore` than the one given to `try_new` still keeps its
  own set; hand both the same `Arc`. `PolicyStore::digest()`,
  `schema()` and `mentions_context()` follow a reload, as do
  `PolicyEvaluator::digest()` and `PolicyEvaluator::schema()`.

- **`require_authz!` answers 500 when the policies read `context` and no
  `Arc<dyn RequestContextProvider>` extension is installed.** It used to log
  one warning and decide on an empty context, so a `forbid` written as
  `context has ip && !...` stopped applying and the `permit` beside it
  allowed. The refusal is the same 500 and named error log as a missing
  `PolicyStore`. The check is per store (`PolicyStore::mentions_context`), not
  per action, so every gate on a store whose policies mention `context`
  refuses until the provider is installed; installing the trait object (not the
  concrete provider type) under `Extension<Arc<dyn RequestContextProvider>>`
  fixes it. A store that never mentions `context` is unchanged.

- **Reload steps are bounded.** A follower's `PolicySource` read, each
  `ReloadHook` or cache invalidation, and the announce each stop after a
  limit (30 s, 30 s and 10 s) and are reported as a failed step instead of
  holding the reload lock. Set other limits with
  `AuthzStore::with_reload_timeouts(ReloadTimeouts { .. })`. A source that
  cannot be read, times out or panics now counts on the refused counter
  (`axess_authz_policy_reload_refusals_total`), and the follower carries on;
  alert on that counter.

- **A follower never goes back to an older bundle.** A source that has a
  monotonic version overrides `PolicySource::load_versioned` and returns
  `VersionedBundle::new(bundle).with_generation(n)`; the follower refuses a
  generation below the highest it applied and counts the refusal. A source
  that keeps the default has no generation and behaves as before. A policy
  reload made on a following instance with `reload_policies` and not written
  to the source is replaced by the source's bundle at that instance's next
  notice or poll; write an emergency change to the source.

- **A FIDO2 assertion or registration written in the standard base64
  alphabet is refused.** webauthn-rs 0.6.2 reads every binary field of a
  `PublicKeyCredential` or `RegisterPublicKeyCredential` (`rawId`,
  `authenticatorData`, `clientDataJSON`, `signature`, `userHandle`,
  `attestationObject`) as URL-safe base64, padded or not; the 0.6.0-dev
  reader also took the standard alphabet (`+`, `/`) and arrays of numbers.
  `FactorCredential::as_public_key_credential` answers `None` for such a body
  and the login fails. Browsers' `toJSON()` and the usual WebAuthn client
  libraries send URL-safe base64; a client that encodes by hand with `btoa`
  must switch `+` to `-` and `/` to `_`.

- **`JwtSvidResolver` refuses every token unless it has a tenant lookup or the
  named waiver.** The slug in the SPIFFE `sub` and the `tid` claim are two
  statements by the issuer, and nothing tied them together. Construction is
  unchanged; `resolve` answers `NotAuthenticated` (with a warning naming the
  missing lookup) until you set one:

  ```rust,ignore
  // before
  JwtSvidResolver::new(verifier, trust_domain, token)
  // after, with your tenant registry
  JwtSvidResolver::new(verifier, trust_domain, token)
      .with_tenant_lookup(|slug| tenants.id_of(slug))
  // after, where you trust the issuer to keep the two claims consistent
  JwtSvidResolver::new(verifier, trust_domain, token).without_tenant_cross_check()
  ```

- **A back-channel logout token ends only the verifying tenant's sessions.**
  The login path now records the tenant beside each `sid` mapping and
  subject record, and a token verified by a tenant's provider reads only that
  tenant's. A token verified by a global provider is unscoped, as before.
  A record made with `None` (a global provider's login) is invisible to a
  tenant provider's token, as that provider did not sign it.

- **`StoredDelegationSession::revoke` waits for a refresh in flight** (it
  takes the refresh lock), so it can take as long as the token endpoint's
  timeout. After it returns, no later `get_access_token` succeeds. A store
  that implements `save_if_unchanged` also keeps a revoke from another
  process from being undone; one that does not is ordered by the lock within
  one process only.

- **A custom tenant provider source can be unseen by the back-channel route
  for up to 30 seconds after a provider is added.** The route remembers an
  issuer no provider is configured for, so an anonymous loop of such requests
  costs one tenant-source read per interval. `LiveTenantOAuthProviders` and
  `StoredTenantOAuthProviders` change the new `TenantOAuthProviders::generation`
  on every upsert, reload, removal and invalidation, which voids a remembered
  miss, so a provider added through them is found at once. A source of your
  own that does not override `generation` (it defaults to a constant), or a
  store another process writes, is found once the interval has passed:
  override `generation` to return a number that changes with every change, or
  shorten the memory with `BackChannelLogoutHandler::with_unknown_issuer_memory`
  (a zero duration remembers nothing). Put `RateLimitLayer` on the route in
  any case.

- **Impersonations in flight at the upgrade end.** An impersonation now stands
  on the administrator's standing: `begin_impersonation` registers an entry
  for the administrator in the session registry, and the session layer reads
  it on every request. An impersonation begun by 0.17.0 has no such entry, so
  its next request is refused and the administrator begins it again. The
  entry is removed by `end_impersonation`, and with the administrator's other
  sessions when they are suspended, deleted or ended; a registry that holds
  sessions for a bounded time keeps the entry alive while the impersonation is
  in use. It counts as one of the administrator's registered sessions for
  `with_max_sessions_per_user`.

- **Tenant OAuth providers are screened, and a loopback or private issuer
  stops working.** `StoredTenantOAuthProviders` now refuses an issuer URL
  that is not HTTPS or that names a loopback, private, link-local,
  unique-local, shared-address or metadata address, refuses any endpoint its
  discovery document names under the same rule, and refuses a connection to a
  host name that resolves to such an address. `upsert` refuses the record up
  front; a record written past it is refused when its provider is built, with
  an `OAuthError::Config` naming the setting and the range. A deployment that
  federates with an identity provider on its own network names the opt-out;
  tests against a mock on the loopback interface use the test opt-in:

  ```rust,ignore
  use axess::federation::oauth::EgressPolicy;
  // an internal IdP, trusting everyone who can write a provider record
  let tenants = StoredTenantOAuthProviders::new(store, cipher)
      .with_egress_policy(EgressPolicy::unscreened());
  // wiremock on 127.0.0.1 in a test
  let tenants = StoredTenantOAuthProviders::new_unencrypted(store)
      .with_egress_policy(EgressPolicy::screened_allowing_loopback_http());
  ```

  A provider you build yourself with `OAuthProviderConfig::discover` keeps
  the old rule (HTTPS, or loopback HTTP); use `discover_screened` for an issuer
  a tenant supplied.

- **Expired unverified signups are swept on a schedule you run.**
  `purge_expired_candidates(limit)` deletes the `Candidate` accounts past the
  lifetime below that nobody asked for again, one `AccountDeleted` audit row per
  deletion; call it from a timer and again while it returns `limit`.

- **An unverified signup expires.** A `Candidate` account older than 24 hours
  (`DEFAULT_CANDIDATE_TTL`, `with_candidate_ttl` on the builder, never shorter
  than `with_signup_verification_ttl`) no longer reserves its identifier: the
  next `begin_signup` for it deletes the row and starts afresh, with an
  `AccountDeleted` audit row. `begin_signup` stamps `created_at` with the
  service's clock, so the age does not depend on the time in the record you
  pass. A candidate nobody asks for again stays as a row; purge those with
  `delete_user` as before.

- **A passing factor no longer clears the guess throttle.** The delay earned
  by wrong guesses is cleared when the whole login completes, not when one
  factor passes. A login whose password step passes and whose second factor
  fails no longer resets the delay for the next attempt, so a sequence of such
  attempts is delayed as a sequence of wrong guesses at one factor always was.

- **A new reset request no longer invalidates a live link.** An account holds
  up to `DEFAULT_MAX_LIVE_RESET_TOKENS` (3, `with_max_live_reset_tokens`) live
  reset tokens at once. A request beyond that stores nothing, leaves the earlier
  links alone, answers `Ok(None)` and is audited as `live_tokens_full`; using
  any one token consumes all of the account's tokens. Alert on
  `live_tokens_full`, which also shows a third party asking for resets on an
  account. The per-instance cooldown record, which a flood of made-up identifiers could
  fill to refuse every reset on the instance, now drops its oldest cooldown
  when it is full: a refusal falls only on an identifier that is itself
  cooling down, and the mail one account can be sent is bounded by the live-token
  limit instead.

- **The JWKS refresh covers tenant providers and runs eight at a time.**
  `refresh_all_jwks` and the refresh loop now include the providers a tenant
  registry holds built (`LiveTenantOAuthProviders`, `StoredTenantOAuthProviders`)
  through `TenantOAuthProviders::built_providers`. A pass refreshes up to
  `JWKS_REFRESH_CONCURRENCY` providers at once, so a slow endpoint holds back
  its own slot only.

- **A user holds at most 32 `Unknown` devices.** When a request with a user
  and no valid device cookie would create a device, the user's least recently
  seen `Unknown` devices beyond `DEFAULT_MAX_UNKNOWN_DEVICES_PER_USER` are
  deleted first (`with_max_unknown_devices_per_user` changes the bound). `Seen`
  and `Trusted` devices are never evicted.

- **`BearerError::UntrustedIssuer` carries a bounded, escaped issuer.** The
  text is cut to `MAX_ISSUER_ECHO_BYTES` (128) and control characters are
  escaped; match on the variant, not on the full issuer text.

- **`require_authz!` names the step-up a denial needs.** A policy carrying
  `@step_up("<name>")` makes the gate answer 403 with
  `{"error": "step_up_required", "step_up": "<name>"}` instead of
  `{"error": "Access denied"}` when that step-up would permit the request.
  Without `@step_up` annotations nothing changes. A policy set whose
  annotation names no step-up is refused at build and at reload with
  `AuthzError::PolicyValidation`.

- **A FIDO2 ceremony in flight across the upgrade is refused.** Ceremony state
  is typed by its ceremony now, and state 0.17 stored does not read: the
  finish answers `InvalidCredential` (login) or `NoFlow` (registration) and the
  user begins again.

- **A session created before 0.18 carries no assurance.** It satisfies no
  policy that reads `context.assurance` until it logs in again or steps up;
  its other state, including `factors_completed`, is kept.

- **A FIDO2 login offers only the credentials its ceremony accepts.** With the
  default passkey ceremony that is every passkey, as before; a login ceremony
  that fits none of the user's credentials is `NoFlow`.

### New, not breaking

- `SidStore`, `ValkeySidStore`, `AuthnServiceBuilder::with_sid_store`,
  `AuthnService::sid_store`, `LogoutReplayLog`, `ValkeyReplayLog`,
  `BackChannelLogoutHandler::with_replay_log` and `with_metrics`: share the
  back-channel logout state between instances. See
  [OAuth: back-channel logout across instances](../../factors/oauth.md).
  The handler constructors still take a `SidMap`; `with_sid_store(authn.sid_store())`
  on the handler points it at the shared store.
- `envelope_aad_v2`, `envelope_aad_for` and `EnvelopeFields` in `axess-events`
  bind status, actor, time, envelope version, trace context, algorithm and key
  id into the AAD of an encrypted event. `axess-events` does no sealing, so
  nothing changes by itself: your seal path passes whichever AAD it asks for.
  `envelope_aad` (the first tag, which leaves those fields unauthenticated) is
  now deprecated and warns where you call it; seal with `envelope_aad_for`,
  and open with `open_aads_for`, which lists the second tag then the first so
  events sealed before still open.
- `FactorAssurance`, `CredentialBinding`, `StepUp` and
  `AuthSession::assurance`: what each factor proved and when, recorded on the
  session at login and at every step-up.
- `AssuranceContext`, `AssuranceContextProvider`, `ASSURANCE_SCHEMA_FRAGMENT`
  and `merge_assurance_schema`: the record in the Cedar context as
  `context.assurance`, with its schema types.
- `AuthzRefusal`, `AuthzSession::require_with_step_up` and
  `RequestAuthnService::begin_step_up_for`: the refusal that names a step-up,
  and the call that begins it with the ceremony it names.
- `Fido2Ceremony`, `begin_fido2_registration_with`,
  `DefaultFido2Provider::with_trust_anchor` and
  `with_presence_only_security_keys`: the ceremony chosen per operation.
  The design behind these four items is
  [Authentication assurance and ceremonies](../../authorization/assurance.md).
