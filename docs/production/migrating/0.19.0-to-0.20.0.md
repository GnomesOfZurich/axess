# 0.19.0 to 0.20.0

Upgrade every node together. A 0.19.0 node and a 0.20.0 node do not see each
other's sessions: this release stores a session under a key derived from its
id, where 0.19.0 stored it under the id, and the session registry and the
sid store name it by that key too. During any overlap, a revocation made by
one release (a suspension, a logout, a kick, a logout sent by an identity
provider) does not reach the sessions of the other. Stop every node of the
earlier release before the first node of this one serves a request, and let
the audit archive drain finish first (see "The audit archive drain finishes
before the upgrade" under "Behaviour changes").

Every session is signed out once at the upgrade. No session stored before
0.20.0 is carried over, and a rollback to 0.19.0 finds none of the sessions
0.20.0 stored. Refresh tokens are another store and still work. Plan the
deployment for a quiet hour.

Entries below that speak of a rolling upgrade (tenant OAuth credentials,
the Valkey authz cache, sealed events) describe a deployment that cannot
avoid an overlap of the two releases; sessions are still not shared across
such an overlap.

The page runs in this order: the change of time types, which reaches most
code that names a time; the other compile breaks; the behaviour changes;
the changed defaults; what is new and breaks nothing; and last, the
defaults and decisions this release leaves where they were. The compiler
finds every site of the first two, and none of the behaviour changes.
Nothing is deprecated: a form this release replaces is removed, and its
entry under "Compile breaks" names the replacement.

### Time types: chrono leaves the public API

Every time axess takes, returns or stores is now a type of `axess-clock`,
built on the standard library alone:

| Type | Holds | Was |
|---|---|---|
| `Timestamp` | a reading of the UTC wall clock to the nanosecond, from `-262143-01-01T00:00:00Z` to `+262142-12-31T23:59:59.999999999Z` | `chrono::DateTime<Utc>` |
| `SignedDuration` | an exact signed span: the difference of two readings, a step of a test clock | `chrono::Duration` (`TimeDelta`) |
| `std::time::Duration` | a configured lifetime, window, grace or tolerance, which cannot be negative | `chrono::Duration`, or a signed count of seconds |
| `Until` | an end that comes at a reading or never: `Until::At(..)` or `Until::Forever` | a `DateTime<Utc>` clamped to chrono's latest instant |
| `UtcDate` | the calendar day in UTC a reading falls on | `chrono::NaiveDate` |

The facade and the core re-export them, with the crate's error type:
`axess::{Timestamp, SignedDuration, Until, UtcDate, TimeError}` and the
same under `axess_core::`; test code finds `Shift` in `axess::testing`.
No public signature of any axess crate names chrono, and no conversion to
or from a chrono type (or any other library's) is in the public API, behind
a feature or otherwise. Drop `chrono` from your manifest unless your own
code uses it (see "Using another time library" at the end of this section).
chrono is still compiled into two kinds of build, though it appears in no
axess signature. A build that enables authorization holds it through
Cedar's core (`cedar-policy-core`), and the `axess` facade always enables
authorization. A build that enables OAuth holds it through `oauth2` and
`openidconnect`, which take chrono values, and through the private
conversion in axess-factors that turns a reading into the chrono value
`openidconnect` takes.

Nothing stored or sent changes, except the one response named below: a
reading is written as the RFC 3339 text and the Unix numbers 0.19.0 wrote
(with `Z` and the fewest of 0, 3, 6 or 9 fraction digits; with `+00:00`
where 0.19.0 wrote that form), and every form 0.19.0 read still reads as
the same reading. An end that never comes is written as
`+262142-12-31T23:59:59.999999999Z`, Unix second 8,210,266,876,799, the
value 0.19.0 wrote for a lifetime that did not fit, and exactly that value
reads back as `Until::Forever`. A second of 60 in stored text reads as the
last nanosecond of second 59, with the Unix second 0.19.0 gave it.

The compiler finds every changed signature below, and each entry says what
to write. The changes of behaviour it cannot see are in bold under "Handle
`Until`".

#### Replace `DateTime<Utc>` with `Timestamp`

`Clock::now` returns a `Timestamp`, so a `Clock` of your own changes its
return type. Every `now` parameter, every stamp of a stored type and every
time parameter of a store trait is a `Timestamp`: among them the stamps of
`User`, `Tenant`, `Device` and its bindings, `SessionData`, `StatusDetail`,
`Impersonation`, `WorkflowState`, `EventQueryFilter`, `RefreshToken`,
`StoredDelegation`, `StoredRecoveryCode::used_at`, `Fido2Credential`,
`MintClaims`, the SPIFFE types' validities, `AuthEventBuilder::build_at`,
`AuthnError::into_response_at`, `DeviceStore::claim_owner`,
`DeviceStore::replace_bindings`, `DeviceStore::set_trust_level_if`,
`verify_totp`, `verify_recovery_code`, `verify_dpop_proof`,
`DpopJtiCache::try_insert` and `parse_datetime_flexible`, which returns
`Option<Timestamp>`. A store of your own that keeps a time in a column
writes `at.unix_seconds()` (or `to_rfc3339()` for text) and reads
`Timestamp::from_unix_seconds(n)` (or `Timestamp::parse_rfc3339(&text)`).

| chrono | axess-clock |
|---|---|
| `Utc::now()` | `clock.now()`, from the `Clock` the code is handed (`SystemClock` in production) |
| `DateTime::from_timestamp(secs, nanos)` | `Timestamp::new(secs, nanos)`, or `Timestamp::from_unix_seconds(secs)`, `from_unix_millis`, `from_unix_micros`, `from_unix_nanos`: each an `Option` |
| `Utc.with_ymd_and_hms(y, m, d, h, min, s).unwrap()` | `Timestamp::from_utc(y, m, d, h, min, s)`, a `const fn` that answers `None` for a day the calendar does not have |
| `at.timestamp()`, `at.timestamp_millis()`, `at.timestamp_micros()` | `at.unix_seconds()`, `unix_millis()`, `unix_micros()`, each rounded down, also before 1970; `unix_nanos()` is an `i128` |
| `at.timestamp_subsec_nanos()` | `at.subsec_nanos()` |
| `at + span`, `at - span`, `at.checked_add_signed(span)` | `at.checked_add(span)`, `at.checked_sub(span)`: no operators, since one could only panic past the range |
| `a - b`, `a.signed_duration_since(b)` | `a.since(b)`, a `SignedDuration`, defined for every pair |
| `DateTime::parse_from_rfc3339(text)` | `Timestamp::parse_rfc3339(text)`, which reads any offset into UTC and every form 0.19.0 read |
| `at.to_rfc3339()` (`+00:00`) | `at.to_rfc3339_numeric_offset()` |
| the `Z` text serde wrote | `at.to_rfc3339()`, and `Display` and serde (feature `serde` of `axess-clock`) write the same |
| `at.year()`, `at.month()`, `at.day()`, `at.hour()` | `at.utc_date().year()`, or `at.to_utc()` for the date, hour, minute, second and nanosecond at once |
| `DateTime::<Utc>::MIN_UTC`, `MAX_UTC` | `Timestamp::MIN`, `Timestamp::MAX`: the ends of the range, nothing more; an end that never comes is `Until::Forever` |

A `Timestamp` in a message prints as RFC 3339 text with `Z`
(`2023-11-14T22:13:20Z`), where chrono printed `2023-11-14 22:13:20 UTC`.

#### Replace `chrono::Duration` with `std::time::Duration` or `SignedDuration`

A configured lifetime, window, grace or tolerance is the standard library's
`std::time::Duration`, as the other configured lifetimes of the crates
already were, so a negative one can no longer be written:

- `RefreshTokenConfig::ttl`, `RefreshTokenConfig::max_lifetime`,
  `RefreshTokenConfig::reuse_grace` and `RefreshTokenConfig::with_max_lifetime`;
- `ProfileValues::refresh_ttl` and `ProfileValues::refresh_max_lifetime`;
- `SweepConfig::trusted_idle`, `SweepConfig::seen_idle` and
  `SweepConfig::revoked_grace`, the getters and the builder setters;
- `DeviceLifecycleService::with_sighting_granularity`;
- the skew of `StoredDelegation::is_fresh`;
- `LocalIdp::with_max_ttl`, `LocalIdp::max_ttl`, `LocalIdpFixture::with_max_ttl`,
  `LocalIdpFixture::max_ttl` and `DEFAULT_MAX_TTL`, and the cap in
  `IssuanceError::LifetimeExceedsCap::max`;
- `StoredDelegationSession::with_refresh_skew_secs(i64)` is
  `StoredDelegationSession::with_refresh_skew(Duration)`, still held to one
  day at most;
- `DpopVerifyRequest::max_iat_skew_secs` and
  `DpopProofRequest::max_iat_skew_secs` (an `i64` of seconds) are
  `DpopVerifyRequest::max_iat_skew` and `DpopProofRequest::max_iat_skew`,
  each a `Duration`, and `MAX_IAT_SKEW_SECS` is `MAX_IAT_SKEW`.
  The skew is still counted in whole seconds, as `iat` is, so a fraction of
  a second in it changes nothing, and one above `MAX_IAT_SKEW` still makes
  every verification fail;
- `RequestProofCheck::max_age_secs` and `RequestProofCheck::max_ahead_secs`
  (`i64` seconds) are `RequestProofCheck::max_age` and
  `RequestProofCheck::max_ahead`, each a `Duration`, counted in whole
  seconds as before.

Write `Duration::from_secs(60)`, `Duration::from_mins(5)` or
`Duration::from_hours(24)`; thirty days is `Duration::from_hours(30 * 24)`.
`RefreshTokenConfig::validate` refuses a `ttl` or a `max_lifetime` of no
time ("ttl must be positive", "max_lifetime must be positive"), and can no
longer answer "reuse_grace must not be negative".

A span that may be negative stays signed, as a `SignedDuration`: the
difference of two readings (`now.since(at)`,
`IssuanceError::LifetimeExceedsCap::observed`), a step of
`MockClock::advance`, and the `ttl` of `LocalIdpFixture::mint_jwt_svid` and
`mint_jwt_svid_at`, which may be negative so a test can mint a token that
has expired. `SignedDuration::seconds`, `minutes`, `hours`, `days` (86,400
seconds each), `milliseconds`, `microseconds` and `nanoseconds` build one;
`checked_add`, `checked_sub`, `checked_mul` and `checked_div` answer `None`
outside the range; `whole_seconds`, `whole_milliseconds` and
`unsigned_abs` read it; and `Display` prints it as chrono did (`PT7200S`,
`PT1.5S`), so `IssuanceError::LifetimeExceedsCap` prints the text of
0.19.0. `checked_div` divides the whole span at once and is exact, where
chrono's division of a span with a fraction could be a nanosecond off.
`SignedDuration::try_from(duration)` and `Duration::try_from(span)` convert
between the two; the second refuses a negative span.

`LifetimeFault::NonPositiveCap` is `LifetimeFault::ZeroCap`, since a cap can
no longer be negative, and its message is "the max-TTL cap is no time".

#### Counts of seconds are `Duration`s

A bound or a setting held as an integer count of seconds is a
`std::time::Duration`, with the `_secs` or `_seconds` suffix dropped:

- the fixed bounds `jwt::claims::MAX_IAT_AGE_SECS`,
  `logout_token::MAX_IAT_AGE_SECS`, `MAX_IAT_FUTURE_SECS` and
  `JTI_RETENTION_SECS` (an `i64` each) are `jwt::claims::MAX_IAT_AGE`,
  `logout_token::MAX_IAT_AGE`, `MAX_IAT_FUTURE` and `JTI_RETENTION`, and the
  testing constant `device_key_parsers::GRACE_SECS` is
  `device_key_parsers::GRACE`;
- `ValidationConfig::leeway_secs` and `MAX_LEEWAY_SECS` are
  `ValidationConfig::leeway` and `MAX_LEEWAY`;
- `FapiConfig::max_id_token_lifetime_secs` is
  `FapiConfig::max_id_token_lifetime`;
- `SignerSpec::assertion_ttl_secs` is `SignerSpec::assertion_ttl`, and
  `ClientAssertionSigner::with_assertion_ttl` returns a `Result`;
- `EmailOtpConfig::ttl_secs`, `MIN_EMAIL_OTP_TTL_SECS` and
  `MAX_EMAIL_OTP_TTL_SECS` are `EmailOtpConfig::ttl`,
  `axess_factors::MIN_EMAIL_OTP_TTL` and `axess_factors::MAX_EMAIL_OTP_TTL`;
- `TotpConfig::period_secs` is `TotpConfig::period`, and
  `TotpVerifyParams::period`, `TOTP_PERIOD` and the `period` argument of
  `build_totp_uri` and `build_totp_uri_with_algorithm` are `Duration`s;
- `AssumeRoleWithWebIdentityRequest::duration_seconds` and
  `AssumeRoleWithWebIdentityRequest::with_duration_seconds(u32)` are a
  private field, read with `AssumeRoleWithWebIdentityRequest::duration()`,
  and `AssumeRoleWithWebIdentityRequest::with_duration(Duration)`, which
  returns a `Result` (below), with the range AWS takes as
  `AssumeRoleWithWebIdentityRequest::MIN_DURATION` and
  `AssumeRoleWithWebIdentityRequest::MAX_DURATION`. A struct literal of the
  request no longer compiles: build it with `new` and the `with_` methods;
- `OidcError::JwksExpired { age_secs, max_age_secs }` is
  `OidcError::JwksExpired { age, max_age }`, both `Duration`s (`age` to the
  millisecond); its message reads as before, in whole seconds.

What is stored and sent keeps its bytes: a `TotpConfig`, an
`EmailOtpConfig` and a `SignerSpec` write and read `period_secs`,
`ttl_secs` and `assertion_ttl_secs` as the same integers, the provisioning
URI writes `period=30`, the STS call sends `DurationSeconds=900`, and the
replay record of a logout token expires after the same 360 seconds.

Where a protocol or a stored form counts whole seconds, a value with a
fraction of a second, or outside the protocol's bounds, is refused by name
where it is configured, never rounded:

- `verify_jwt` refuses a `ValidationConfig` whose `leeway` has a fraction,
  as it refuses one above `MAX_LEEWAY`, and so refuses a `JwtVerifier`
  whose `with_clock_skew` has one (a security profile's `jwt_leeway`
  included), with `JwtError::VerificationFailed` naming the leeway;
- `verify_totp` refuses a `period` of no time or with a fraction, and
  `build_totp_uri` answers `None` for one with a fraction as it did for
  one under five seconds;
- `prepare_factor` refuses an email code `ttl` with a fraction, as it
  refuses one outside the bounds;
- `ClientAssertionSigner::from_spec` and
  `ClientAssertionSigner::with_assertion_ttl` refuse a lifetime of no time
  or with a fraction with the new `ClientAssertionError::AssertionTtl`;
- `AssumeRoleWithWebIdentityRequest::with_duration` refuses a duration with
  a fraction or outside 900 to 43200 seconds with the new
  `AwsStsError::InvalidDuration`, where it is configured: write
  `.with_duration(d)?`. No request can then hold one, and the call sends
  what was set.

A stored form also refuses, when written, a span it cannot hold. The FAPI
cap is compared with the whole seconds of `exp - iat`, so a fraction in it
changes nothing.

#### Handle `Until`

An end that a lifetime may carry past the range is an `Until`, so code and
tests can tell "never" from a far year:

- `RefreshToken::expires_at`, `SignupVerification::expires_at()` and
  `WorkloadApiEvent::WithdrawalDeferred::until` are an `Until`;
- `LockoutPolicy::lockout_until` returns `Option<Until>`, and so does
  `DerivedLockout::until`;
- `StatusDetail::until` and `StatusDetail::with_until`,
  `AuthnError::Locked::until`, `FactorOutcome::Locked::until`,
  `LoginOutcome::Locked::until`, `WorkflowState::verification_expires_at`
  and `WorkflowState::with_verification` hold `Option<Until>`, and
  `AuthnError::lockout_expiry()` returns one;
- in axess-factors, `HotpConfig::locked_until()` returns `Option<Until>` and
  `EmailOtpConfig::pending_until` is one.

Compute an end with `Until::after(now, lifetime)`: `Until::At(now +
lifetime)`, or `Until::Forever` when the sum runs past the range. Read one
with `until.is_past(now)` (never true for `Forever`), `until.at()` (the
reading, or `None` for `Forever`), a `match` on the two variants, or a
comparison that wraps the reading: `Until::At(now) >= until`, since every
`At` orders before `Forever`. Store one as `until.to_timestamp()` (text) or
`until.unix_seconds()` (a column of seconds), which give the value 0.19.0
stored, and read it back with `Until::from_timestamp(at)` or
`Until::from_unix_seconds(n)`.

**A lock that never ends sends no `Retry-After`.** A lockout whose duration
runs past the range is `Until::Forever` both where it is counted from now
(`LockoutPolicy::lockout_until`) and where it is counted from the last
failure (`LockoutPolicy::derived_lockout`, which gave `until: None` for it).
The default response (`AuthnError::into_response_at`, feature
`default-error-response`) to such a lock writes no `Retry-After` header,
since the header can only state a time; 0.19.0 sent the number of seconds
to the year 262142. The body still states the end as `until_iso`, the
latest reading with `+00:00`, as before. A lock that ends at a reading is
answered as before. Only a policy not held to `LockoutPolicy::MAX_DURATION` by
`LockoutPolicy::bounded` can reach this. The service bounds every tenant's
policy, so a caller of `derived_lockout` with a policy of its own sees it.
A device-key registration window or acceptance grace too long to hold also
never ends, rather than panicking or ending at once.

#### `SystemTime` conversions are fallible

`std::time::SystemTime` starts in 1601 on Windows and ends at other years
on other platforms, so neither side holds the other's whole range:
`SystemTime::try_from(at)` and `Timestamp::try_from(system_time)` answer
`TimeError::OutOfRange` where the other side cannot hold the value.
`SystemTime::from(clock.now())` does not exist; write
`SystemTime::try_from(clock.now())`. Code that must have a reading and has
no way to refuse takes `Timestamp::from_system_time(system_time)`, which
gives the nearer end of the range instead.

#### `UtcDate` for a calendar day

`FilesystemAuditArchiver::path_for_date` takes a `UtcDate`, where it took a
`chrono::NaiveDate`. `UtcDate::new(2026, 1, 31)` builds one (`None` for a
day the calendar does not have), `at.utc_date()` gives the day a reading
falls on, `year()`, `month()` and `day()` read it, and
`UtcDate::days_since_epoch` and `UtcDate::from_days_since_epoch` count
whole days from 1970-01-01. It has no other arithmetic; a library of
calendars is the place for that.

#### Tests

`MockClock::at` and `MockClock::set` take a `Timestamp`,
`MockClock::reference_time` returns one, and `MockClock::advance` takes a
`SignedDuration`. `Shift` (in `axess_clock::testing` and `axess::testing`)
gives a test `at.plus(span)` and `at.minus(span)`, which return the shifted
reading and panic outside the range. A `const` reading is
`const T: Timestamp = Timestamp::from_utc(2026, 1, 1, 0, 0, 0).unwrap();`,
checked when the test compiles.

#### Features of axess-factors

`tracing` is an optional dependency, enabled by the features whose code
logs (`password`, `totp`, `fido2`, `mtls`, `jwt` and every feature built on
one of them), and `testing` no longer enables it. `jwt` no longer enables
`tokio`: a build of `axess-factors` with `jwt` alone that relied on it for
`tokio` now names `tokio` as its own dependency.

#### Using another time library

You may keep chrono, `time`, jiff or any other time library on your side.
axess does not convert to their types: you convert at your boundary,
through what both sides hold. There are three ways, and each works for any
library that reads and writes the form:

- Unix seconds and nanoseconds: `Timestamp::new(secs, nanos)` and
  `at.unix_seconds()` with `at.subsec_nanos()`, or one `i128` of
  nanoseconds with `Timestamp::from_unix_nanos` and `at.unix_nanos()`;
- `std::time::SystemTime`, through the conversions above;
- RFC 3339 text: `at.to_rfc3339()` and `Timestamp::parse_rfc3339`.

A `Clock` may read any source: implement its one method, `now`, over your
library's reading of the time, converted by one of the three.

The examples below are `axess-clock/tests/other_time_library.rs` without
its header; axess-clock's tests compile and run them. First the standard
library:

```rust,ignore
use axess_clock::{Clock, SignedDuration, Timestamp};
use std::time::{Duration, SystemTime};

const NEW_YEAR: Timestamp = Timestamp::from_utc(2026, 1, 1, 0, 0, 0).unwrap();

/// Unix seconds and nanoseconds: the reading as two numbers, and back. Each
/// constructor answers `None` outside the range of a `Timestamp`.
#[test]
fn through_unix_seconds_and_nanoseconds() {
    let at = NEW_YEAR
        .checked_add(SignedDuration::milliseconds(250))
        .expect("inside the range");
    let (secs, nanos) = (at.unix_seconds(), at.subsec_nanos());
    assert_eq!((secs, nanos), (1_767_225_600, 250_000_000));
    assert_eq!(Timestamp::new(secs, nanos), Some(at));
    assert_eq!(Timestamp::from_unix_nanos(at.unix_nanos()), Some(at));
    assert_eq!(Timestamp::from_unix_seconds(i64::MAX), None);
}

/// `std::time::SystemTime`, both ways fallible: on some platforms it starts
/// later or ends sooner than a `Timestamp`. `Timestamp::from_system_time`
/// takes the nearer end of the range instead of refusing.
#[test]
fn through_system_time() {
    let system = SystemTime::try_from(NEW_YEAR).expect("a system time on this platform");
    assert_eq!(Timestamp::try_from(system), Ok(NEW_YEAR));
    assert_eq!(Timestamp::from_system_time(system), NEW_YEAR);
}

/// RFC 3339 text: `to_rfc3339` writes the `Z` form, `parse_rfc3339` reads
/// any offset and gives the reading in UTC.
#[test]
fn through_rfc3339_text() {
    assert_eq!(NEW_YEAR.to_rfc3339(), "2026-01-01T00:00:00Z");
    assert_eq!(
        Timestamp::parse_rfc3339("2026-01-01T01:00:00+01:00"),
        Ok(NEW_YEAR)
    );
}

/// A configured lifetime is the standard library's `Duration`; a difference
/// of two readings is a `SignedDuration`. Between the two, a negative span
/// is refused.
#[test]
fn spans_through_the_standard_library() {
    let lifetime = Duration::from_secs(900);
    let span = SignedDuration::try_from(lifetime).expect("fits a signed span");
    assert_eq!(span, SignedDuration::minutes(15));
    assert_eq!(Duration::try_from(span), Ok(lifetime));
    assert!(Duration::try_from(SignedDuration::seconds(-1)).is_err());
}
```

Then chrono, with a `Clock` over a source of chrono readings:

```rust,ignore
/// chrono, through Unix seconds and nanoseconds. chrono keeps a leap second
/// as a fraction of a whole second or more, which a `Timestamp` does not
/// have: it is read as the last nanosecond of second 59, as
/// `Timestamp::parse_rfc3339` reads a second of 60.
fn from_chrono(at: chrono::DateTime<chrono::Utc>) -> Option<Timestamp> {
    Timestamp::new(at.timestamp(), at.timestamp_subsec_nanos().min(999_999_999))
}

fn to_chrono(at: Timestamp) -> Option<chrono::DateTime<chrono::Utc>> {
    chrono::DateTime::from_timestamp(at.unix_seconds(), at.subsec_nanos())
}

#[test]
fn chrono_through_unix_seconds_and_nanoseconds() {
    let at = NEW_YEAR
        .checked_add(SignedDuration::nanoseconds(1))
        .expect("inside the range");
    let theirs = to_chrono(at).expect("chrono holds the reading");
    assert_eq!(theirs.to_rfc3339(), "2026-01-01T00:00:00.000000001+00:00");
    assert_eq!(from_chrono(theirs), Some(at));
}

/// chrono, through RFC 3339 text.
#[test]
fn chrono_through_rfc3339_text() {
    let theirs: chrono::DateTime<chrono::Utc> =
        NEW_YEAR.to_rfc3339().parse().expect("chrono reads it");
    assert_eq!(Timestamp::parse_rfc3339(&theirs.to_rfc3339()), Ok(NEW_YEAR));
}

/// A `Clock` over a source of the adopter's own: here a function that
/// returns chrono readings, converted through `SystemTime`, which never
/// fails. In production the source is `chrono::Utc::now`; a test hands it a
/// fixed reading.
struct SourceClock(fn() -> chrono::DateTime<chrono::Utc>);

impl Clock for SourceClock {
    fn now(&self) -> Timestamp {
        Timestamp::from_system_time(SystemTime::from((self.0)()))
    }
}

#[test]
fn a_clock_over_another_source() {
    let clock = SourceClock(|| chrono::DateTime::from_timestamp(1_767_225_600, 0).expect("a date"));
    assert_eq!(clock.now(), NEW_YEAR);
}
```

For another library the rule is the same: find which of Unix seconds and
nanoseconds, `SystemTime` or RFC 3339 text it reads and writes, and convert
through that. axess's tests build no other library, so this page shows no
method of one.

### Compile breaks

- **`LocalIdpSigningKey::generate_rsa` (or another `generate_rsa*`, a
  `from_rsa_*` loader, `LocalIdpFixture::new_rsa`): "no function or
  associated item named `generate_rsa` found".** The local IdP's RSA keys
  are behind a feature of their own, `local-idp-rsa`, and `local-idp`
  alone no longer compiles the `rsa` crate, which carries
  RUSTSEC-2023-0071. To keep RSA, enable `local-idp-rsa` beside (or in
  place of) `local-idp` on `axess` or `axess-core`; nothing else changes.
  Or move to ES256, which needs no feature: `generate_es256`,
  `from_ec_pem`, `LocalIdpFixture::new`. `LocalIdpFixture::with_algorithm`
  with `RS256`, `RS384` or `RS512` compiles without the feature and
  panics there (`try_with_algorithm` answers `UnsupportedAlgorithm`).

- **An exhaustive `match` on `PrincipalRejection`: "non-exhaustive

  below version 3 is not served (see "No session stored by an earlier
  release is served" under "Behaviour changes").
- **`StandardRequestContext` has a fifth public field,
  `StandardRequestContext::key_bound`.** A
  struct literal of it names the field (`None` emits nothing) or is built
  with `new` or `at`, as the documentation shows.
- **`DeviceRequest::presented` is a slice of `PresentedDevice`**, the
  entries of the device cookie newest first, where it was one optional
  entry. A resolver of your own that builds a `DeviceRequest` passes `&[]`
  for none and `std::slice::from_ref(&entry)` for one, or every entry its
  cookie holds (`PresentedDevice::parse_all`).
- **A struct literal of `DeviceRequest`: "missing field `keys` in
  initializer of `DeviceRequest<'_>`".** The field says whether device keys
  are enforced for the request and what the request proved. A resolver of
  your own adds `keys: KeyEnforcement::of(&parts)`
  (`axess::device_key::KeyEnforcement`), which reads what the session layer
  left in the request and is the one constructor outside tests. Under a
  layer that enforces device keys, `resolve_or_keep` and `resolve_proven`
  then prove a device that has a key only by that key; under any other
  layer the field enforces nothing and a device is proven by its token as
  in 0.19.0.
- **`DeviceRequest::fingerprint` is an `Option<FingerprintHash>`**, where
  it was the hash: a struct literal that passes the hash fails with
  "mismatched types". A resolver of your own passes `Some(hash)`, and `None` for a
  request it cannot fingerprint, which `resolve_or_keep` and
  `resolve_proven` resolve by its token, its key or its session's device as
  any other and give no new device.
- **The error of `LifecycleDeviceResolver` is
  `LifecycleResolveError<S::Error>` where it was the device store's
  error.** Code that calls its `resolve` and names or matches the error
  reads the store's error from `LifecycleResolveError::Store(e)`;
  `TenantMissing` is the authenticated request for which `tenant_fn`
  answered no tenant (under "Behaviour changes").
- **A struct literal of `ProfileValues`: "cannot construct
  `ProfileValues` with struct literal syntax due to private fields"
  (`ProfileValues::device_key_proof_ttl`,
  `ProfileValues::device_key_challenge_ttl`).** `ProfileValues` keeps the
  profile it came from in a private field (`ProfileValues::profile`, under
  "Added"), so no struct literal outside axess builds it, and it gains two
  public fields, the lifetimes `ProfileValues::device_key_config` applies.
  Start from `SecurityProfile::values()` and assign the fields that differ;
  the standard profile's values for the two new fields are 10 and 20
  minutes.
- **A struct literal of `TenantOAuthProviderRecord`: "missing field `kind`
  in initializer of `TenantOAuthProviderRecord`"
  (`TenantOAuthProviderRecord::kind`).** The field is the
  `FederatedProvider` every login through the tenant's provider records.
  Add `kind: None` for the 0.19.0 behaviour, a login recorded as
  `Custom(name)`, or name the kind (`kind:
  Some(FederatedProvider::Microsoft)`). A stored record is read and written
  as before: `None` is not written, and a record without the field reads
  as `None`.
- **`AxessMetrics` (`axess_core::AxessMetrics`,
  `axess_core::metrics::AxessMetrics`) asks for a ninth concern,
  `DeviceKeyMetrics`.** A type
  that implemented the eight concern traits to be handed to
  `MetricSinks::all` no longer satisfies `AxessMetrics`; add
  `impl DeviceKeyMetrics for YourExporter {}` (every method defaults to
  nothing), or count the device-key signals. A type handed to the concerns
  one by one is not affected.
- **`ProvenDevice` is a struct with private fields.** It was a tuple struct
  whose field was private too, so nothing outside the library built one;
  `ProvenDevice::proof` is new and says whether the device was proven by
  its token or by its key.
- **`TraceIdLayer` or `TraceIdMiddleware`: "unresolved import
  `axess_core::TraceIdLayer`", "cannot find type `TraceIdMiddleware`".**
  The two were other names for `TraceContextLayer` and
  `TraceContextMiddleware`, and are removed. Write `TraceContextLayer`
  (`axess_core::TraceContextLayer`, or `axess::trace_context::TraceContextLayer`
  through the facade) and `TraceContextMiddleware`; the layer, its
  constructors and what it does are the same.
- **The feature `trace-id`: "package `your-app` depends on `axess` with
  feature `trace-id` but `axess` does not have that feature".** The feature is
  `trace-context`, on `axess` and on `axess-core`. Change it in
  `Cargo.toml`:

  ```toml
  axess = { version = "0.20", features = ["trace-context"] }
  ```

- **`axess_core::middleware::trace_id` or `axess::trace_id`: "could not
  find `trace_id` in `middleware`", "unresolved import `axess::trace_id`".**
  The module is `axess_core::middleware::trace_context`, and
  `axess::trace_context` in the facade, with the same items in it. The
  crate-root re-exports are unaffected: `axess_core::TraceContextLayer`
  and `axess_core::TraceContext` are where they were.
  An import by the old module path changes its module only:
  `trace_id::TraceContext`, `trace_id::TraceContextLayer` and
  `trace_id::TraceContextMiddleware` are `trace_context::TraceContext`,
  `trace_context::TraceContextLayer` and
  `trace_context::TraceContextMiddleware`; `trace_id::TraceIdLayer` and
  `trace_id::TraceIdMiddleware` have no successor of their own name (the
  entry above says which type takes each one's place).

### Behaviour changes

- **Request-guard log lines name the matched route, not the path.** The
  refusal lines of `CsrfLayer` (no session, a foreign Origin, a missing or
  invalid token, a cross-site WebSocket upgrade), the session layer's
  WebSocket Origin refusal and the trace line of `NoopDeviceResolver` carried
  the request's path (`path`) or its whole URI (`uri`), and a path or a query
  can carry a credential such as an invitation token. They now carry a
  `route` field: the template the router matched (`/invites/{id}`), read
  from axum's `MatchedPath`, or `-` when no router matched, as for a layer
  wrapped around the whole router or a route reached through
  `nest_service`. A log query that read `path` on these lines reads `route`;
  add the layers with `Router::layer` to get the template.

- **`axess-core`'s `sqlx` feature enables the `sqlx` dependency.** The
  feature asks `axess-identity` for the `sqlx` derives of the id types,
  which expand to `sqlx` items, and a build that named `sqlx` without a
  store did not compile. Nothing changes for a build that names a store,
  which enabled the dependency already.

- **With a `PrincipalResolverChain` installed, every step runs for every
  request, and the steps must agree.** A request that presents a signed-in
  session and a workload credential, or the credentials of two different
  workloads, is refused with 401 (`PrincipalRejection::ConflictingCredentials`)
  by `AuthPrincipal`, `AuthHumanPrincipal` and `AuthWorkloadPrincipal`
  alike, whichever step comes first; a credential any step refuses refuses
  the request, even when another step resolved someone. **Migrating:** a
  client sends one credential, or the credentials of one principal. With
  no chain installed the extractors read the session alone, as in 0.19.0.

- **`require_authz!` reads one `AuthzInstallation`.** The gate decides with
  the policy store, the entity provider and the context provider of one
  value, built by `AuthzInstallation::new` and added to the router as a
  layer. Before:

  ```rust,ignore
  let store = Arc::new(PolicyStore::from_text(policy_text, schema_json)?);
  let entities: Arc<dyn RequestEntityProvider> = Arc::new(entities);
  let context: Arc<dyn RequestContextProvider> = Arc::new(context);
  let app = Router::new()
      .route("/ledgers/{id}", get(view).layer(require_authz!(
          "MyApp", "ViewLedger", "Ledger:{id}",
          validator = authn.session_validator())))
      .layer(Extension(context))
      .layer(Extension(store))
      .layer(Extension(entities));
  ```

  After:

  ```rust,ignore
  let store = Arc::new(PolicyStore::from_text(policy_text, schema_json)?);
  let installation = AuthzInstallation::new(
      store,
      Arc::new(entities),
      Some(Arc::new(context)),   // None when no policy reads `context`
  )?;
  let app = Router::new()
      .route("/ledgers/{id}", get(view).layer(require_authz!(
          "MyApp", "ViewLedger", "Ledger:{id}",
          validator = authn.session_validator())))
      .layer(installation);
  ```

  The three `Extension` layers are not read any more: a router that keeps
  them and adds no installation compiles and answers 500 at every gate,
  with the error "no AuthzInstallation in the request". Every router that
  carries a gate needs the installation, a hand-built one included.
  `AuthzInstallation::new` returns `AuthzError::ContextProviderRequired`
  when the policies read `context` and the third argument is `None`: pass
  the provider. An application that reloads policies passes a provider even
  when today's policies read no `context`, because a reloaded set that
  begins to read it is otherwise refused by the gate (500 per request)
  until the read is gone again. Hand the same `Arc<PolicyStore>` to
  `AuthzInstallation::new` and to `AuthzStore::try_new` so a reload reaches
  the gates.

- **A stored delegated credential is used only with the registration it
  was granted through.** `StoredDelegation` carries the `registration`
  (`GrantRegistration`) of the grant that created it, and every refresh
  keeps it. `StoredDelegationSession::get_access_token` compares it with
  the provider the session was built with and refuses any other
  registration, one of the same name included (another tenant's `mail`, a
  shared `mail`), with `DelegatedError::RegistrationMismatch`: nothing is
  sent to that registration's token endpoint, and a still-fresh access
  token is not handed out either. Before, the store's key was the provider
  name alone, so a refresh token granted through one registration was sent
  with another's client credentials to its token endpoint. A credential
  stored by an earlier release has no registration, and the library does
  not guess one: it is refused the same way, fresh or not, and the user
  grants again. Route `RegistrationMismatch` to the reconnect flow, as
  `RefreshRejected` is. `EncryptedDelegatedCredentialStore` writes
  envelope version `v4`, which binds the registration into each token's
  associated data, so a row moved under another registration does not
  open; a `v3` row opens as granted through no registration, and is
  re-sealed as one by the read that finds it. A store of your own persists
  `registration` beside the other fields and gives it back on `load`
  unchanged; one that drops it makes every credential it holds unusable.

- **A `private_key_jwt` client with an RSA key is refused unless its
  signature is chosen.** Without `jwt-aws-lc`, `ClientAssertionSigner::new`,
  `from_pem` and `from_spec` answer `ClientAssertionError::RsaNotChosen` for
  `RS256` to `RS512` and `PS256` to `PS512`, before the key is read: there
  the signature would run in `rsa` 0.9, whose private-key operations leak
  timing (RUSTSEC-2023-0071). With `jwt-aws-lc` the signature runs in
  aws-lc-rs, and an RSA signer is built only where the `jsonwebtoken` crypto
  provider in place is the aws-lc one axess installed. Where the application
  or another crate installed a provider first, axess cannot tell which
  library signs, and the same three constructors answer `RsaNotChosen`. In
  0.19.0 an RSA signer was built on either backend. The refusal reaches
  whatever builds the signer: an outbound client, a provider built
  `with_private_key_jwt`, a tenant's stored provider when the directory opens
  it. To keep the RSA key on `jwt-rust-crypto`, enable `client-assertion-rsa`
  on `axess` (or `axess-core`, `axess-factors`), which chooses that
  signature. On `jwt-aws-lc`, leave installing the provider to axess; where
  your own code signs or verifies with `jsonwebtoken` before axess does, call
  `axess_factors::jwt::ensure_crypto_provider()` first in place of an install
  of your own, or enable `client-assertion-rsa`. Or move the client to an
  ES256, ES384 or EdDSA key and register its public half at the identity
  provider.

- **A request that sends no device cookie no longer reads as proven.** The
  library's `LifecycleDeviceResolver` used to answer `BoundDevice::Proven`
  for the device an authenticated session was bound to when the request
  presented no token, so the session cookie alone stood in for the device:
  `AuthSession::proven_device` answered for it, and with it the per-account
  lockout's exemption for a device the account has used. Whoever held a copy
  of a session cookie could guess that account's password past the lock and
  the throttle, in a password entry or a step-up answered in one request.
  Now a device is proven only by the request that presents its token, or the
  request it is created on. A request without the token still keeps the
  session's device (no second device is created, and everything that reads
  the device by its id, the step-up decision and the passkey paths among
  them, is unchanged), as `BoundDevice::Unproven`. Who notices:
  - a client that never sends the device cookie (a cookieless API client, a
    browser that drops it) no longer reads as proven after its first
    request, and so no longer has the lockout exemption;
  - a visit that arrives from another site reads as recognised on that
    request and as proven again on the next one from the site itself;
  - a session issued from a refresh token stays unproven until a request
    presents the device token, as it was meant to;
  - code that reads `AuthSession::proven_device` or
    `SessionData::device_proven` to gate something of its own is now
    answered per request, and should ask on the request that does the gated
    thing;
  - `SessionData::device_proven` is no longer serialised: a stored row does
    not carry it, and a session is no longer rewritten when only that
    answer changes;
  - a resolver of your own built on
    `DeviceLifecycleService::resolve_proven` is answered `None`, where it
    was answered the session's device, for a request of an authenticated
    session that presents no token. Call `resolve_or_keep` and hand its
    `bound()` to the session layer to keep that device as recognised.

- **A `DeviceStore` of your own implements `sweep`; an `Err` no longer
  stands for a sweep that was not written.** The trait documentation used
  to allow a backend to answer `Err(_)` with a "not yet implemented"
  sentinel. No shipped store did, and the sentence is gone: a store that
  answers `Err` from `sweep` reports a store failure, and one that never
  sweeps leaves trusted devices trusted and revoked rows unpurged for ever.
  The contract is stated on the method: one call moves a row one level at
  most, each window counts from the stamp the step before wrote, only the
  tenant's rows are read, an `Unknown` row is never moved, and the counts
  are the rows that call wrote. `SweepCounts` gains `SweepCounts::skipped`: the rows a
  call met and could neither decide nor move (a row that does not decode,
  a due row whose write stayed contended), which the Valkey store used to
  pass over with an `Ok` that read as "nothing was due". Zero in every count
  says that nothing was due. A struct literal or an exhaustive pattern of
  `SweepCounts` adds the field ("missing field `skipped`"); a store that
  decides each row inside one statement reports zero. A store that
  returned a sentinel implements the sweep; `SweepConfig::level_after` and
  `purge_due` are the decisions to apply to each row.

- **A tenant's provider needs a redirect URI of its own.** A callback is
  finished only on the route of the registration the login began with, and
  for a provider a tenant brought that route names the tenant:
  `OAuthCallbackRoute::of_tenant(&tenant, provider)`. Two tenants may each
  have a provider called `sso`, and a provider name alone did not tell
  their callbacks apart, so a tenant whose identity provider is hostile
  could send a user on to another tenant's honest one, which sends no
  `iss`, and have the code that came back posted to its own token endpoint.
  A deployment whose tenant records all share one redirect URI
  (`/auth/callback/{provider}`) cannot name the tenant from the request and
  has to change: give each record a `redirect_url` with the tenant in the
  path (`/auth/callback/{tenant}/{provider}`) or in the host name, register
  that URI at the tenant's identity provider, and read the tenant in the
  callback handler from the path or the host the server routed, never from
  a query parameter, a body or the session. A callback on another tenant's
  route, on the global route for a tenant's provider, or on a tenant's
  route for a global provider is refused as `OAuthError::CsrfMismatch`
  before the code is exchanged, with a `provider_mismatch` login-failure
  row, and the ceremony is cleared. A login begun with `begin_oauth_login`
  or `begin_oauth_login_in_tenant` runs against the global registration and
  finishes on `OAuthCallbackRoute::global(provider)`.

- **An impersonated session's device is the administrator's.** When an
  administrator impersonates a user, the session's browser is the
  administrator's, and the first impersonated request used to give that
  browser a device owned by the user (displacing the user's oldest `Unknown`
  device at the cap), which a later step-up could promote. Now nothing an
  impersonation does creates, claims, promotes or trusts a device for the
  user. Who notices:
  - a `DeviceResolver` or `user_fn` of your own that reads `SessionUser` is
    handed the administrator for an impersonated session, where it was
    handed the user; read `AuthSession::user_id` for the user the session
    runs as;
  - `AuthSession::user_device` answers `None` under impersonation, so the
    documented promote call writes nothing there;
  - a refresh token issued under impersonation (only with
    `with_impersonated_credential_changes_allowed`) names no device,
    whatever `device_id` the call is given;
  - a device row a past impersonation left under a user stays until the
    sweep or a revocation removes it: no row is rewritten.
- **Under the FAPI profile with `SenderConstraint::Mtls`, the token, PAR,
  userinfo and revocation requests follow the egress policy of discovery.**
  The client that presents the certificate used to be a plain client: it
  followed `HTTPS_PROXY` from the environment and resolved names without the
  address screen, whatever policy `discover_screened` ran under. It is now
  built by that policy, so a screened provider's mTLS requests go direct and
  refuse a reserved address. An advertised `mtls_endpoint_aliases` entry on
  a reserved address is refused by discovery, as it was in 0.19.0, and
  `build` repeats that check on the alias it installs. A deployment that reached
  its bank's mTLS endpoints through an egress proxy names the opt-out it
  already needed for discovery, `EgressPolicy::unscreened()`, and filters at
  the proxy.

- **An endpoint named through a builder setter follows the egress policy of
  discovery.** `with_par_endpoint`, `with_revocation_endpoint`,
  `with_end_session_endpoint` and `with_device_authorization_endpoint` were
  held to the transport rule only, so a provider discovered under a screened
  policy took a literal private, link-local, metadata or other reserved
  address there. `build` now checks each one as discovery checks the
  endpoints its document names, and refuses with `OAuthError::Config`
  naming the setting and the range, never the URL. A host name passes and
  is screened on the addresses it resolves to when the request is made. A
  provider that names such an endpoint on its own network is discovered
  with `discover_screened` and `EgressPolicy::unscreened()`.

- **A discovery document or key set answered through a redirect is refused.**
  `DiscoveryDocument::fetch`, `Discovery::fetch`,
  `JwksCache::fetch` and `JwksCache::refresh` go through a
  client that follows no redirect, and refuse an answer whose status is
  `3xx` with `OidcError::DiscoveryFetch` or `OidcError::JwksFetch` naming
  the redirect, where the fetches of 0.19.0 followed one when the client
  they were handed did. An issuer whose well-known URL redirects (to add a
  trailing slash, say) must be configured with the URL it finally answers
  from.

- **`begin_grant` and `complete_grant` refuse a delegated provider whose
  `redirect_uri` is anything but HTTPS, or HTTP to a loopback host, or
  that carries userinfo** with `DelegatedError::Transport` naming
  `redirect_uri`, as they already refused such an authorization or token
  endpoint. The IdP sends the browser back to that URL with the code and
  the `state`. Plain HTTP to a remote host is refused, and so are every
  other scheme (a private-use scheme of a native application, say) and an
  HTTPS URL with a user name or a password in it. HTTP to `localhost`, to
  an IPv4 loopback address such as `127.0.0.1` and to `[::1]` stays
  allowed for development.

- **The egress screen judges two more IPv6 forms by the IPv4 address they
  carry.** An IPv4-translated address (`::ffff:0:a.b.c.d`) is the IPv4
  address in its last 32 bits, and a Teredo address (`2001::/32`) is judged as
  the client address it carries (inverted) when that address is reserved,
  and as `private` otherwise, so `https://[::ffff:0:169.254.169.254]/` and a Teredo
  tunnel to a private client are refused by name.

- **The text an identity provider answers a refusal with is escaped and
  cut before it reaches an outcome or an error.**
  `DeviceTokenOutcome::Denied` carries the token endpoint's
  `error_description`, or its `error` code when there is no description,
  with every character `axess_identity::log_text::escapes` names written
  as an escape (a control character, U+2028 or U+2029, a bidirectional
  control, a zero-width character, the byte order mark, a Hangul filler)
  and cut to 512 bytes, `...` marking the cut. The `error` code of a
  refused device
  authorization request (`OAuthError::DeviceAuthorization`), of a refused
  `client_credentials` grant (`OAuthError::TokenExchange`) and of a
  verified JARM refusal (`JarmResponse::error`) is escaped the same way
  and cut to 128 bytes, as is the code a refused revocation logs. The
  refusal text of the authorization-code and refresh grants
  (`OAuthError::TokenExchange`) is escaped the same way and cut to 1 KiB,
  and the PAR endpoint's is its first 1 KiB, escaped, so at most
  `ERROR_SNIPPET_LOG_BYTES`. The token, device, revocation and PAR
  requests, the delegated refresh, and the Azure and AWS STS clients read
  up to 64 KiB of a refusal, where 0.19.0 read 1 KiB, and the OAuth paths
  take its `error` code member by member. A description up to 64 KiB long,
  before or after the code, therefore no longer turns `invalid_grant`,
  `unsupported_token_type` or `authorization_pending` into a bare status,
  a delegated refresh's `invalid_grant` into a plain
  `DelegatedError::TokenEndpoint` instead of `RefreshRejected`, or an STS
  code into `unknown`. Only the reading grew, not what reaches an error or
  a log line. The AWS STS client reads an error document element by
  element, the first element of a name counting, so a document cut at
  64 KiB still names a code that came before the cut. A `Code`, `Type` or
  `RequestId` interrupted by the cut, or by a point that is not well-formed
  XML, is not kept, so the start of one code never reads as another;
  a `Message` keeps its text up to that point. Where 0.19.0 parsed the
  document whole and read `Unknown`, a document with a `Code` but no
  `Message` now reads as that code with an empty message, one that stops
  being well-formed after its `Code` keeps that code, and a `Message`
  holding an element reads as all of its text. A refusal with no code
  still reads as `Unknown`, its message now starting
  `error body with no code: ` where it started `non-XML error body: `.
  `http_body::ErrorBody`, under "Added", reads a refusal the same way for
  a client of your own; `read_for_status` still returns the first 1 KiB
  of a refusal, for formatting. A code or a description with no control
  character and under its bound reads as it did, surrounding space and an
  empty AWS `Code` included, so a comparison with `access_denied` or
  `expired_token` still holds; code that matched a longer text, or showed
  it to a user, sees the escapes and the cut.
  `log_safe`, under "Added", is the same sanitiser for text of your own.

  The public error fields outside the identity-provider paths changed the
  same way. `GcpError::Sts.body`, `GcpError::IamCredentials.body`,
  `DelegatedError::TokenEndpoint.body` and
  `OAuthClientError::TokenEndpoint.body` hold the first 1 KiB of the
  response body, as they did, now with the same characters written as
  escapes and not cut again, so at most
  `ERROR_SNIPPET_LOG_BYTES`. A `body` field is no longer the raw body: a
  line break in it is the two characters `\n`, and a body that spans lines
  does not parse. Code that parsed one of these fields as JSON must stop;
  it branches on the HTTP status the variant carries and logs the text. In
  `AwsStsError::StsError` the `code`, the `fault_type` and the
  `request_id` are escaped and cut to 128 bytes each and the `message` to
  512, where 0.19.0 copied them whole; a body that is not XML is escaped
  and cut to 512 bytes inside `message`.

- **A provider name nothing resolves is carried escaped and cut.**
  `OAuthError::UnknownProvider` held the name the caller passed whole, and
  a refresh under such a name wrote it whole into the failure row's
  `factor_kind` (`FederatedProvider::Custom`). The name is often the
  request's own text, the `{provider}` of a route, so both now carry it as
  the call's span does: the characters `log_text::escapes` names written
  as escapes and cut to 128 bytes, `...` marking the cut. A registered name
  with no control character and within 128 bytes reads as it did, so a
  comparison with the name you passed still holds for those; the rows of a
  refresh whose provider resolved name it as registered.

- **A response, token or proof that does not parse is reported with
  serde's message cut.** serde quotes the value it could not read (`invalid
  type: string "...", expected u64`), escaped but whole, so a 2xx answer
  with a long string where a number belongs put all of it into one error.
  The parse errors of the token, userinfo, PAR and device responses, the
  discovery document and the key set, a JWT or logout-token payload, a
  JOSE header, a DPoP proof, the social and outbound clients, the cloud
  STS answers and the delegated grants now keep the first 256 bytes of
  serde's message, escaped, with `...` at the cut, followed by the
  position serde reported (` at line 1 column 61443`) whole. A message
  under the bound reads as it did. `log_safe_parse_error`, under "Added",
  is the same for a parse of your own.

- **More text a remote party or a request wrote is carried escaped and
  cut.** The same treatment now reaches: the `htm` and `htu` of a refused
  DPoP proof, both the claim and the request's own (64 bytes each); the
  `kid` of `JwtError::UnknownKid` and the issuer of
  `BearerError::UntrustedIssuer`, which were cut and are now escaped as
  well, with the `...` of the cut inside `MAX_KID_ECHO_BYTES` and
  `MAX_ISSUER_ECHO_BYTES` (128) where it used to follow them; the `typ` of
  a refused logout token (64); the `issuer` and `jwks_uri` a discovery
  document names, in `OidcError::InvalidIssuer`, `OidcError::NonHttpsIssuer`
  and the key-set log lines (256); `LdapError::Directory::text` and the
  text of `LdapError::Search` and `LdapError::Connection` (256); and the
  identifier quoted by `IdentityError::InvalidSpiffeId`,
  `InvalidTrustDomain` and `InvalidComponent` (64, in `axess-identity`,
  where the JWT-SVID and mTLS resolvers take an identifier apart; the
  tenant slug the JWT-SVID resolver logs, 128). Control characters, the
  Unicode line and paragraph separators, bidirectional controls,
  zero-width characters, the byte order mark and the Hangul fillers are
  written as escapes. The `...` of a cut stands inside the bound, so a cut
  value keeps fewer whole characters than the bound has bytes: 40 copies
  of `é` are quoted by `IdentityError::InvalidSpiffeId` as 30 and `...`,
  not 32. A value under its bound with none of those characters reads as
  it did; a test that matched a longer value whole matches its head.

- **`JarmResponse`'s `Debug` output redacts the authorization code and the
  `state`.** `{:?}` of a verified JARM response prints `Some("[redacted]")`
  for a `code` or a `state` that is present, where 0.19.0 printed the
  values: the code redeems for tokens and the `state` is the ceremony's
  CSRF value. The fields are public and unchanged. A log line or a test
  that took either from the `Debug` text now reads the field instead, and
  logs neither value.

- **`SqliteTenantOAuthProviderStore::init_schema` can refuse at start-up.**
  It now adds a generated `client_id` column to a `tenant_oauth_providers`
  table an earlier release created and a unique index over
  `(issuer, client_id)`. Rows that already hold one pair more than once (two
  tenants registered the same client of the same issuer under an earlier
  release, or one tenant registered it twice under two names, which already made
  that client's back-channel logout ambiguous and refused) are reported by
  name in the error and logged at error level, and the index is not created
  over them. Remove or re-point all but one record of each pair, then start
  again. A store of your own must enforce the same uniqueness atomically and
  answer `TenantOAuthProviderStoreError::pair_held()` (see the trait docs);
  `StoredTenantOAuthProviders::upsert` turns it into the `OAuthError::Config`
  refusal its own in-process check already gives.

- **One record per `(issuer, client_id)` pair, whoever owns it.** The rule
  is the store's: `StoredTenantOAuthProviders::upsert` now refuses a
  tenant's own second record of a pair it already holds under another
  provider name, which 0.19 allowed (and which made that client's logout
  tokens ambiguous just the same). A tenant that wants a second name for one
  client re-points or removes the first record. The refusal text reads
  "already registered by another record" where 0.19 said "another tenant";
  the global registration's refusal is unchanged.

- **Tenant OAuth credentials are re-sealed when the directory starts.**
  The sealed credential of a `TenantOAuthProviderRecord` is now bound to
  the redirect URL, the scopes, the DPoP mode, the credential's kind and
  the signer spec as well as the issuer and client id. A record sealed by
  0.15 to 0.19 (bound to the issuer and client id only) is moved to the
  full binding by `StoredTenantOAuthProviders::started` (see "Changed
  defaults"), and, under the `Accept` opt-in, by its first use as well,
  exactly as a credential under a rotated key is. The move is one-way:
  0.19.0 cannot open a credential that 0.20.0 has sealed or re-sealed. A
  0.19.0 process that shares the store stops building every tenant's
  provider, with `OAuthError::Store` carrying `FactorSecretError::Open`,
  once a 0.20.0 directory has started, so a rolling upgrade keeps short the
  time the two releases serve tenant logins side by side, and sets
  `Accept` on the 0.20.0 side while 0.19.0 nodes still write. A rollback
  to 0.19.0 needs the `tenant_oauth_providers` rows from a copy taken
  before the upgrade, or each credential upserted again under 0.19.0. A
  store of your own whose `put_if_revision` returns
  `put_if_revision_unsupported()` moves nothing: the pass counts each such
  record in `ResealReport::not_moved` and names it in a warning, the
  record stays readable by 0.19.0, and under the default it is refused at
  use (see the `put_if_revision` entry under
  [Compile breaks](#compile-breaks)). The first release's binding
  (`with_first_binding`) keeps its own policy and default.

- **A token revocation through `oauth_for_session` or `oauth_in_tenant`
  writes a request row and an outcome row, and is not sent when the request
  row cannot be written.** `revoke_oauth_token` on either scope asked the
  provider and wrote nothing in 0.19.0. It now writes two `LogoutAttempt`
  rows that name the provider (as `factor_kind`), carry the session's user
  and the tenant where the scope has them, and share a `request_id`: the
  audit context's, or one drawn for the revocation when the context has
  none. The request row is written before the provider is asked; it is a
  `Failure` with the reason `OAUTH_REVOCATION_REQUESTED_REASON`
  (`oauth_token_revocation_requested`), so a request whose outcome was
  never recorded does not read as a revoked token. The outcome row follows
  the provider's answer: `Success` when it revoked the token, `Failure`
  with a reason starting `oauth token revocation refused` when it refused,
  and `Failure` with a reason starting `oauth token revocation unconfirmed`
  when it did not answer (a timeout, a connection lost after the request
  was sent, a server error), since the token may then be revoked or not.
  Pair the rows by `request_id` and read the outcome row. When the request
  row cannot be written the call returns `OAuthError::AuditStore` and
  nothing is sent. When the outcome row cannot be written it returns
  `OAuthError::AuditStore` too, after the provider was asked, with a
  message that says what the provider answered; the token may then be
  revoked, and the trail shows the request alone. RFC 7009 answers a token
  already revoked as it answers a live one, so sending the revocation again
  records its outcome. A row the audit pipeline sheds (`AuditOutcome::Shed`)
  counts as written, as in every audited flow: the revocation goes ahead
  and the shed is counted in the audit metrics. A consumer that counts
  `LogoutAttempt` rows as logouts now counts token revocations too, two rows
  each, and `factor_kind` alone tells them apart: a revocation's rows name
  the provider there, and a logout's row carries no `factor_kind`. The
  `session_id` field (the session's key) does not tell them apart: a
  logout's row carries it, and so do
  a revocation's rows whenever the audit context has one, as an
  `AuditContext` extracted behind the session layer does. The by-name
  `AuthnService::revoke_oauth_token`, which wrote no row, is removed (see
  "Compile breaks").

- **`delete_fido2_credential` answers `Ok(true)` when the passkey is removed
  and its credential-id claim could not be released.** 0.19.0 released the
  claim before it wrote the audit row and returned the store's error
  (`AuthnError::Store`) with no row, though the passkey was already gone.
  The `FactorDisabled` row is now written as soon as the removal commits,
  the release follows, and a release the store refuses is logged at `warn`
  and does not fail the call. An audit write that fails is the error
  the call returns, after the release was tried, and is logged at `error`
  as a passkey removed without its row, naming the tenant and the user:
  the error alone does not say the passkey is gone. A claim the store
  keeps stays with that user: they can register the id again; another
  account of the tenant cannot until the store releases it. An error from
  this method no longer stands for a failed release; an operator who needs
  the id freed reads the `warn` line, which names the tenant and the user.

- **Applying a security profile never loosens.** In 0.19.0 every method of
  `ProfileValues` that takes a configuration assigned the profile's value
  over the one the configuration held, a tighter one included, and
  `authn_service_builder` replaced the whole `Fido2Options` with the
  defaults plus the profile's `max_authn_age`. For every
  setting where one value is tighter than another, each now keeps the
  tighter of the configuration's own value and the profile's:
  - a lifetime, a window or a clock-skew tolerance is the shorter of the
    two: `refresh_config` (the sliding and the absolute lifetime),
    `device_cookie_config`, `access_token_verifier` and `jwt_leeway_only`
    (the leeway), and the password reset lifetime and its cap in
    `authn_service_builder`;
  - a limit that may be absent is the shorter of the two, and any limit
    beats none: the refresh family's absolute lifetime, the passkey-change
    recency (`fido2_options`, `authn_service_builder`), the socket lifetime
    (`watch_options`) and the impersonation recency;
  - the Argon2id cost takes the larger memory and the larger number of
    passes of the two and keeps the builder's lanes, so neither component
    comes out lower than either side had it.

  Settings with no order are assigned as before: the `typ` that
  `access_token_verifier` requires and the CSRF origin list, which
  `csrf_config` takes at the call. A default reset lifetime is never left
  above the cap in force. The methods that build a configuration
  from nothing (`session_config_builder`, `auth_rate_limit_builder`,
  `cached_device_store`, `egress_policy`) carry the profile's values, as
  before. Applying a profile twice is applying it once. Who notices:
  - a value tightened before the profile was applied is kept, where 0.19.0
    overwrote it; code that applied the profile first and tightened after it
    sees no change;
  - an attested or security-key ceremony and a ceremony timeout set on the
    builder before the profile are kept, where 0.19.0 reset them to the
    passkey ceremony and 300 s; an application that relied on the profile
    to reset the ceremonies sets them after applying it;
  - `fido2_max_authn_age = None` on `ProfileValues` names no limit and
    leaves the one the options hold, the library's five minutes included,
    where 0.19.0 wrote the `None` through; and a `max_authn_age: None`
    written on the builder before the profile is tightened to the profile's
    value, as 0.19.0 overwrote it;
  - a value loosened on `ProfileValues` past the one the configuration
    holds (a refresh lifetime of sixty days applied to a
    `RefreshTokenConfig` at its thirty) leaves the configuration's in
    force, where 0.19.0 wrote the profile's.

- **A service built under a security profile is held to it.**
  `ProfileValues::authn_service_builder` records the profile on the
  builder, and `AuthnServiceBuilder::build` refuses a service whose
  Argon2id cost, password reset lifetime or cap, impersonation recency or
  passkey-change recency is looser than the value of the profile the values
  came from. In 0.19.0 a setter called after the profile, or a field
  assigned looser on the values before applying, loosened the service in
  silence, and nothing recorded that a profile had been applied. Now the
  profile is a property of the service: `AuthnService::security_profile`
  says which it runs under. The service holds every setting the profile
  governs at the profile's value or tighter, except the waived ones that
  `AuthnService::profile_deviations` lists. Who notices:
  - code that applies a profile and then loosens one of the five settings
    (a `with_argon2_cost` below the profile's, a `with_fido2_options` with
    `max_authn_age: None`, a longer `with_max_password_reset_ttl`) panics at
    `build` with a message naming the profile and the setting, and gets
    `AuthnBuildError::BelowProfileFloor` from `try_build`;
  - so does code that assigns one of those fields looser on `ProfileValues`
    before applying: the builder is held to the profile the values came
    from (`ProfileValues::profile`), not to the values as edited;
  - the one way below the profile is a waiver written out per setting,
    `waive_profile_floor(ProfileSetting::Fido2MaxAuthnAge)` and its
    siblings. A waived setting that is below the profile's value is logged
    once at `warn` when the service is built and listed by
    `AuthnService::profile_deviations`:

    ```rust,ignore
    let authn = SecurityProfile::Strict
        .values()
        .authn_service_builder(AuthnService::builder(identity, factors))
        // No recency requirement for passkey changes, and it says so.
        .with_fido2_options(Fido2Options { max_authn_age: None, ..Fido2Options::default() })
        .waive_profile_floor(ProfileSetting::Fido2MaxAuthnAge)
        .build();
    ```

  - tightening after the profile, and every setting the profile does not
    govern, is unaffected. The settings a profile applies to values the
    service never sees (session, refresh, CSRF, rate limit, JWT verifier,
    device cookie, socket) are covered by the entry above, at the call.

- **A default password reset lifetime above the cap is refused when the
  service is built.** `with_password_reset_ttl` above
  `with_max_password_reset_ttl` used to build, and every
  `begin_password_reset_with_default_ttl` then answered
  `AuthnError::Internal`, so account recovery was down until someone read
  the error. `try_build` now answers
  `AuthnBuildError::PasswordResetTtlAboveCap`, naming both settings, and
  `build` panics with it, under a profile or not. Shorten the default or
  raise the cap.

- **`CsrfConfig::require_origin` refuses an empty list.** A call with no
  origin left the allow-list empty, which the request-time gate reads as
  "no Origin check", and on a config that already named origins it turned
  the check off without a word. It now panics, as it already did when every
  origin it was given failed to parse. A caller whose list may be empty
  decides before it calls: leave `require_origin` out to run without the
  check.

- **A later factor step answers an administrative suspension as
  `Locked { until: None }`.** `verify_factor` and `prepare_factor` on a
  flow whose first factor has passed used to answer every `Suspended`
  state as `Locked { until }` with the suspension's end, so a caller who
  held the password learned that an operator held the account and until
  when. The end is now shown only for a suspension whose cause is
  `StatusCause::Lockout` (a store that keeps the counter's lockout as a
  state); an administrative hold, a pending verification or a closure
  answers `Locked` with no end, as an indefinite lockout does. The audit
  row is unchanged. A form that showed "suspended until" from this answer
  shows "try again later"; the operator's hold is communicated by the
  operator. The passkey ceremonies (`finish_discoverable_login`, the two
  registration steps, `delete_fido2_credential`), `complete_oauth_login`
  and the status read again after a session is registered answer the
  same way: `AuthnError::Locked { until }` carries an end only for a
  `StatusCause::Lockout` suspension, so `lockout_expiry()` is `None` and
  the default response has no `Retry-After` for an administrative hold, a
  pending verification or a closure.

- **`AuthnError::lockout_expiry` reads the end of a
  `NotActive(Suspended(_))` only for a `StatusCause::Lockout`.** The paths
  that still answer in that shape (a suspended tenant, reached from a signup
  or an impersonation; `complete_signup` for an account suspended after
  `begin_signup`; an impersonation whose administrator or target is
  suspended) used to hand the end of an operator's hold to the helper, and
  the default response sent it as `Retry-After` and `until_iso`. The helper
  now answers `None` for any other cause, so the response carries neither.
  Code that read the end of an administrative hold from the error reads it
  from the store instead, where an operator's tooling has the right to it.

- **A hidden signup conflict leaves the session pending a signup.** With
  conflicts hidden (the default), `begin_signup` for a taken identifier
  used to leave the session `Guest` while a free identifier's session went
  to `PendingWorkflow(Signup)`, so a follow-up `complete_signup` answered
  `NoFlow` for the one and `InvalidAssertion` for the other. Both sessions
  are now pending a signup: the taken one under a user id that names no
  stored account, with a secret nobody is sent, so `complete_signup` with
  any secret answers `InvalidAssertion` on both and a resubmission begins
  the signup again on both. An application that read "the session is still
  `Guest`" as "the identifier was taken" cannot any more, and should not:
  that reading was the oracle. `SignupOutcome::Started(None)` still says
  no secret was issued, to the application alone.

- **A failed `begin_impersonation` whose anchor entry was not confirmed
  released answers `AuthnError::ExternalService`.** An impersonation the
  session registry does not register, or whose audit row cannot be
  written, does not stand: the session is cleared and the entry registered
  under the administrator (the anchor) is ended. When the registry did not
  confirm that end, 0.19.0 still answered `NoFlow` for the one and the
  audit error for the other, which hid that the entry may still be
  registered and counted against the administrator's sessions. Both now
  answer `ExternalService` with a message that names the anchor, from
  `begin_impersonation_across_tenants` as well; the failure row of a
  refused registration still names `session_not_registered`, and when that
  row cannot be written the answer is still the `ExternalService` naming
  the anchor, with the missing row logged at `error`. A handler
  that matched `NoFlow` here treats the new answer as a failed
  impersonation too (as a response it is `502`, where `NoFlow` is `409`),
  and an operator ends the administrator's sessions, which ends the entry
  with them. A call dropped before the impersonation stands (a client that
  hangs up, a timeout around the call) ends the anchor and the target's
  session on a spawned task, with a `warn` line; dropped outside a Tokio
  runtime it can only log at `error` that the entries stay.

- **A one-placeholder `require_authz!` resource id may not hold `/` or
  `:`.** In a template with two or more placeholders, 0.19.0 refused a
  value holding a character the template uses as a separator; a template
  with one placeholder was left alone, so `Doc:{id}` on one route with the
  id `t1/x` rendered the same resource id as `Doc:{$tenant}/{id}` on
  another with tenant `t1` and id `x`, and a policy written for the plain
  route answered for the split one. A value under a single placeholder
  that holds `/` or `:` is now refused before the policy is asked: the
  request answers HTTP 500 and records a denial under the
  `invalid_resource` reason, as the gate answers every resource id it
  cannot build, so client input that used to render reaches the handler
  as a server error, not a 403. Ids that carry a slash or a colon, such as
  paths or qualified names, are encoded by the application before they
  reach the template, or the template gets a placeholder per part. A
  template that opens a `{` it never closes was never rendered with the
  brace as text; that refusal is now stated in the renderer and pinned by
  a test.

- **Whether `require_authz!` needs a context provider is read from the
  parsed policies.** `PolicyStore::mentions_context` searched the policy
  text for the word `context`. It now walks Cedar's syntax tree of each
  policy and template and answers whether one reads the `context`
  variable. A store whose only use of the word is in a comment inside a
  policy, a string, an attribute name, an entity id or an annotation was
  answered HTTP 500 on every request until a `RequestContextProvider` was
  installed; it is now evaluated on an empty context, as a store that
  reads none always was. A template that reads `context` now counts,
  linked or not, where the text search saw policies only, so a store that
  holds such a template needs the provider in its `AuthzInstallation` (the
  first entry of this section). Nothing changes with a provider installed.

- **`issue_refresh_token_from_login` reads an `authenticated_at` after
  `now` as `now`.** A clock that ran ahead, or a caller's mistake, could
  anchor a family in the future and pass every recency gate for longer than
  any login could. The record's `authn_time` is now at most the time of
  issue.

- **A lockout `duration` is bounded at `LockoutPolicy::MAX_DURATION`
  (one hundred years).** `LockoutPolicy.duration` is a public field that
  nothing checked, and a value above about 8.2e12 seconds panicked the
  verdict that creates a lockout, the one given while the counter store
  is down, and the status check before a factor, with "DateTime +
  TimeDelta overflowed". An end the service counts from now is computed
  by `LockoutPolicy::lockout_until`, which gives `Until::Forever` for a
  duration that runs past the range of a reading: the end of a new
  lockout, the end given under `CounterUnavailable::Lock` while the
  failure counter cannot be read or written, and the end given with a
  refused guess when the counter shows no lockout. The end of a lockout
  already counted is computed by `LockoutPolicy::derived_lockout`, the
  last failure plus the duration, and gives `Until::Forever` in the same
  case, where 0.19.0 read such a sum as a lockout with no end
  (`until: None`); see "A lock that never ends sends no `Retry-After`"
  under "Handle `Until`" above. The service reads every tenant's policy through `LockoutPolicy::bounded`
  before either computation, which clamps a `duration` above the bound to
  the bound. A policy past a bound is reported once per service at error
  level, naming the field and the bound. A lockout meant to last until an
  administrator acts is `duration: None`, which says so by name; a
  hundred years is not a longer way to say it. `LockoutPolicy::validate`
  is the refusal by name (`LockoutPolicyError`) for the place a policy is
  loaded: a tenant table reader, a configuration file, start-up.

- **`LockoutPolicy.max_attempts` is bounded at `LockoutPolicy::MAX_ATTEMPTS`
  (1000) and `attempt_window` may be neither zero nor above
  `MAX_DURATION`.** Either value used to turn the lock off without a word:
  a count no guesser reaches, or a window inside which every failure had
  already expired. `bounded` reads a count above the bound as the bound, a
  zero window as the default window (one hour) and a window above the
  bound as the bound; `validate` refuses each by name. The clamp reaches
  the policy the service applies: the count and the duration a lockout is
  derived from, and the policy handed to `reserve_attempt`. A store that
  applies `attempt_window` itself when it counts failures reads its own
  row, so it calls `validate` where it loads the policy, as the SQLite
  example does at start-up. A deployment that meant "no lockout" says so
  with the throttle alone and a count at the bound, or with its own gate
  in front of the route.

- **An OTP factor's `max_attempts` is read as at most ten.** Email OTP and
  HOTP configs with a larger value (255 was accepted) now lock after ten
  wrong codes, the ceiling RFC 4226 §7.4 recommends; zero still reads as
  the default of five.

- **`HotpConfig.lookahead_window` may be at most
  `axess_factors::MAX_HOTP_LOOKAHEAD` (100).** A stored window above it
  verifies nothing: `verify_hotp` answers `None` and the login service logs
  the bound at error level. Correct the row; a token that has drifted
  further than a hundred steps is resynchronised, not chased.

- **`EmailOtpConfig.ttl` must lie between
  `axess_factors::MIN_EMAIL_OTP_TTL` (60 seconds) and
  `MAX_EMAIL_OTP_TTL` (1800 seconds).** `prepare_factor` refuses to issue a
  code under a config outside the bounds with `AuthnError::NoFlow` and an
  error-level log naming them, as it already refused a `code_length`
  outside 4 to 8. A code that lived for days sat in an inbox for a guesser
  to find.

- **A JWT clock-skew tolerance above `MAX_LEEWAY` (300 s) is
  refused.** `verify_jwt` refuses a `ValidationConfig` whose `leeway`
  is above the bound, and so refuses a `JwtVerifier` whose `with_clock_skew`
  is above it, with `JwtError::VerificationFailed` naming the bound, before any token is
  read. A leeway that large kept an expired token valid for as long as it
  said. Two clocks further apart than five minutes are fixed where they
  run.

- **`RefreshTokenConfig.hash_pepper` must be at least
  `RefreshTokenConfig::MIN_PEPPER_LEN` (32) bytes.** `validate`, and so
  every issue and refresh, refuses a shorter pepper by name, as the
  recovery-code pepper is refused; a one-byte pepper passed before. A
  deployment with a short pepper moves it to `previous_hash_pepper` (which
  keeps its non-empty minimum, so the rotation is possible) and sets a
  32-byte `hash_pepper`; tokens are re-stored under the new pepper as they
  are used, and the previous one is dropped after one `ttl`.

- **The Valkey session registry keeps a user's keys in one cluster slot,
  under new names.** A user's sessions are `<prefix>:reg:{<user>}` and their
  registration times `<prefix>:reg-at:{<user>}`, so the user id is the hash
  tag and the keys share a slot under any prefix; the moves of a user's
  sessions are `<prefix>:fwd:{<user>}` and `<prefix>:fwd-at:{<user>}`. A
  member of each set is a session's key, 64 hexadecimal characters, and
  `ValkeySessionRegistry::active_sessions` fails on a member that is not
  one, where it left it out of the list. On a cluster the registry no
  longer needs a hash tag in its prefix; a tag there still works and puts
  every user in one slot. `active_sessions` drops orphaned registration
  times in one `EVAL` script over the user's keys, so a session registered
  on another node meanwhile keeps its registration time and its place in
  the eviction order, and `register` writes the registration time with
  `ZADD NX`, so registering a session again no longer moves it. A server
  that stops running scripts after the registry was built skips the orphan
  step with a `warn` line, and the registry's health check sends a script
  and answers unhealthy for a server that refuses scripts. What 0.19.0 left
  in the registry expires by itself within the registry's lifetime (24
  hours by default); to remove it at once, delete `<prefix>:reg:*` and
  `<prefix>:reg-at:*` whose last part has no braces.

- **The Valkey authz cache (`ValkeyEntityCache`) writes its keys in a new
  layout.** The principal, the tenant, the resource and the action each
  have `|` and `%` percent-escaped; the prefix is written as configured and
  the discriminator is a SHA-256 hash, both as in 0.19.0. The tenant
  segment is `t:` followed by the tenant, empty for a session with no
  tenant, so no tenant and an empty tenant, or a tenant that carries `|`,
  no longer share a key or match each other's invalidation. The key of a
  session with no tenant is the one 0.19.0 wrote, unless its principal,
  resource or action carries `|` or `%`. An entry a 0.19.0 pod wrote for a
  session with a tenant is not read by a 0.20.0 pod, so each such entry
  misses once after the upgrade, and `invalidate` and `invalidate_tenant`
  on a pod of one version do not reach such an entry written by the other
  (`invalidate_resource` and `invalidate_all` do, and so does
  `invalidate_principal` for a principal that carries neither `|` nor
  `%`): during a rolling upgrade those entries live until their TTL (60 s by
  default). Where that window matters, call `invalidate_all` once the last
  0.19.0 pod is gone, or shorten the TTL for the upgrade. The tenant has
  its `:` escaped as well (`%3A`); a `TenantId` holds none, so this changes
  only the keys of a tenant string of your own passed to `invalidate` or
  `invalidate_tenant`.

- **On a Valkey cluster, `ValkeyEntityCache` caches nothing unless its
  prefix has a hash tag.** Without one the entries spread over the nodes,
  where an invalidation's `SCAN` reaches one node and its `DEL` is refused
  across slots, so an entry could outlive the invalidation meant to drop
  it. A clustered client with an untagged prefix now reads the provider on
  every check and says so once at `warn`. Give the prefix a hash tag
  (`with_prefix("{axess}")`) to cache again; on a single node nothing
  changes.

- **The Valkey session store says once that a script did not run.** On a
  cluster whose keys hash to different slots (the default prefix), the
  store's rotation takes its sequenced form without sending the script; the
  store warns on its first such rotation, and the later ones are `debug`
  lines (target `axess::session::valkey`). 0.19.0 warned on every rotation.
  A hash-tag prefix on the store restores the script, as before. The
  registry has no sequenced form (see the entry on its keys).

- **A live tenant reload over a pair another provider holds is refused.**
  `LiveTenantOAuthProviders` keeps an `(issuer, client_id)` pair to one
  provider, as the stored directory does: a tenant reload, an
  administrator's or a `ProviderSource` follower's, whose pair another
  `(tenant, name)` or a global provider holds is refused as
  `ProviderReloadError::PairHeld` and the registry is left as it was. The
  registry asks for no proof of ownership; the operator who installs a provider
  through `reload_tenant_oauth_provider_as` checks it. **Migrating:** give
  each tenant its own client registration; a source that lists one client
  under two keys now has the second refused at each read.

- **The login throttle keys an IPv6 address that carries an IPv4 client on
  that client.** A NAT64 address (`64:ff9b::/96`), an IPv4-translated or
  IPv4-compatible one, a 6to4 address and a Teredo address were keyed on
  their /64, which every client of one gateway, relay site or Teredo server
  shares, so one guesser delayed them all. Each is now keyed as the IPv4
  client it carries, the same key that client has over IPv4, and an address
  under the locally used NAT64 prefix (`64:ff9b:1::/48`) is keyed whole.
  Throttle state a store holds under the old keys is read as no state, so a
  delay running at the upgrade ends early once; nothing needs doing. The
  request rate limiter (`KeyExtractor::ClientIp` and `PeerIp`) keys and
  groups these addresses the same way, through the same classification:
  its buckets for them were the /64 and its groups the /48, shared by every
  client of one gateway. A bucket held at the upgrade starts full under its
  new key.

- **The default device fingerprint reads an IPv6 address that carries an
  IPv4 client as that client.** `DefaultFingerprintExtractor` cut a NAT64,
  IPv4-translated, IPv4-compatible, 6to4 or Teredo address to its /48, which
  every client of one gateway, relay or Teredo server shares, so all of them
  gave one fingerprint input. Each is now cut to the /24 of the IPv4 client
  it carries, as the throttle and the rate limiter key it, and an address
  under the locally used NAT64 prefix (`64:ff9b:1::/48`) to its /120.
  **Migrating:** nothing to change. Clients that reach the service through
  one of these forms get a new fingerprint once, so the device layer sees
  them as a new device once, as it did for IPv4-mapped clients in an
  earlier release.

- **The spans of `begin_login`, `login_with_password`, `begin_signup` and
  `begin_password_reset` carry the tenant identifier once, as `tenant`,
  escaped and cut at 128 bytes.** They carried it twice, as `tenant` in
  Display form (raw, uncut, so a line break in it forged a log line) and as
  `tenant_identifier` in Debug form. A log query that reads
  `tenant_identifier` reads `tenant` instead.

- **A login whose account leaves `Active` while its last factor is being
  verified answers as the check before the step would.** The status read
  again after the session is registered answered every state that may not
  log in as `FactorOutcome::Locked { until: None }` and wrote no row. A
  suspension still answers `Locked` (with the end of a lockout only) and now
  writes the locked `FactorVerified` row; a pending, terminated, archived or
  deleted account is `Err(AuthnError::NotActive(state))` with a failed
  `FactorVerified` row naming `not_active`. The check before a factor step
  (`verify_factor` and `prepare_factor`) refused those states with no row;
  it now writes the same failed `FactorVerified` row, so a dashboard sees
  one row for the state whichever check caught it. `login_with_password`
  answers both as a wrong password, as before.

- **`complete_signup` registers the session before it activates the
  account, and a registry that does not register it answers
  `AuthnError::ExternalService`.** It used to activate first. When the
  session registry then refused the session, it cleared the session and
  answered `AuthnError::NoFlow` with no audit row: the account was `Active`
  after a call that failed, nothing recorded why, and the person could not
  try again because the pending signup was gone. Now the account is
  activated only after the registration. A refused registration writes a
  failed `SignupCompleted` row whose `error` is `session_not_registered`
  (`SIGNUP_SESSION_NOT_REGISTERED_REASON`) and leaves the session pending
  the same signup under a new session id, so the same secret completes it
  once the registry answers. A store that fails to activate the account
  ends the registration just made and leaves the signup pending in the same
  way, with `AuthnError::Store` as before. A handler that read `NoFlow` on
  this path as "start again" now sees `ExternalService` and can ask the
  person to follow the link again.
- **A SPIFFE ID is read by the SPIFFE-ID standard's character rules.**
  `WorkloadId::parse` and `WorkloadId::build` took a `~` in a path segment,
  which section 2.2 of the standard does not allow: an id with one is now
  `IdentityError::InvalidSpiffeId` (`InvalidComponent` from `build`). Going
  the other way, `TrustDomain::new` refused an underscore and a name that
  does not start with a letter or a digit; section 2.1 allows both, so
  `trust_domain_name.example.com` and `_internal` are trust domains now.
  Who notices: a deployment with a `~` in a service or tenant slug, whose
  workload ids no longer parse, and code that relied on `TrustDomain::new`
  to refuse an underscore.
- **`peek_spiffe` and `MtlsResolver` refuse a certificate with more than one
  URI SAN.** They used to count SPIFFE URIs only, so a certificate with one
  SPIFFE ID and a second URI of another scheme passed. The X.509-SVID
  standard has a validator reject any SVID with more than one URI SAN
  (sections 2 and 5.2); the refusal is `IdentityError::InvalidSpiffeId`.
- **`JwtSvidResolver` holds a token to the JWT-SVID standard's algorithms,
  and no longer needs an issuer.** A token signed with an algorithm the
  standard does not list (Ed25519, say) is refused even where the verifier
  was told to accept it for other tokens (section 2.1). A verifier that
  waives the issuer by name, with `allow_any_issuer()`, is accepted: the
  standard defines no `iss` claim, so an SVID may carry none. A verifier
  that neither pins nor waives the issuer is refused as before, and so is
  one with no audience.

- **A refused `login_with_password` leaves a fresh guest session, for a
  known and an unknown identifier alike.** It used to return a wrong
  password's `InvalidCredential` with the session still `Authenticating`
  for an account that exists, under a rotated id, while an unknown
  identifier left the session untouched, so the session and the cookie the
  layer sets for a changed one said which identifiers exist. Every answer
  that is not `Authenticated` or `FactorRequired`, an error included, now
  clears the session and rotates its id. Remove a `session.clear()` you
  added after a refusal. Two things to know: a refused attempt on a session
  that was signed in signs it out, and custom data a guest session held is
  gone after a refusal, as it is after a successful login.

- **`finish_discoverable_login` refuses an assertion that does not name its
  user.** The assertion's user handle must be present and equal to
  `User::webauthn_id` of the `user` passed; a missing handle, another
  account's, or a `user` with no handle on record is refused as
  `AuthnError::InvalidAssertion`, counted as a failed attempt. A browser
  always returns the handle for a discoverable credential. Check that your
  user records keep the handle `begin_fido2_registration` returns, and that
  the `User` you pass carries it; test assertions with `"userHandle": null`
  no longer sign in.

- **A FIDO2 begin retires the earlier ceremony of its kind.**
  `begin_discoverable_login` and its variants, `begin_fido2_registration`
  and its variant, and the FIDO2 `prepare_factor` clear the state an earlier
  begin of the same ceremony stored before they start, so a begin that
  fails (a provider that refuses, a state that does not fit the session)
  leaves no earlier challenge finishable. A passwordless begin that failed
  used to drop the earlier ceremony's tenant and keep its state, which left
  that challenge finishable with no tenant check. Nothing to change unless
  a page relied on finishing a challenge after beginning another.

- **No session stored by an earlier release is served.** In 0.19.0 a stored
  session of an earlier schema version was migrated when it was read, and a
  row that was not MessagePack was tried as JSON. Now a session is stored
  and loaded under its key, sealed under the label `axess.session.v2` where
  the store encrypts, and read only as MessagePack in the shape this release
  writes. A row of 0.19.0 is named by the session id, not the key, so it is
  never found: the request runs as a guest and the row is left to expire.
  `SESSION_DATA_VERSION` is 3, and a row found at a version below it is
  refused whatever it holds: the request runs as a guest, the row is counted by
  `SessionMetrics::session_row_refused`, logged at `warn` by the first eight
  characters of its key, and left to expire. A row at the version in another
  shape (a pending state stored without `flow`, say) and a row that is not
  MessagePack fail to load (`SqlStoreError::Decode` from a SQL store), and
  the request runs as a guest. So every session of 0.19.0 is signed out once,
  and no migration needs to run. 0.19.0 marked a pending step-up by the
  method name `step-up`; now the pending state's `AuthFlow` says whether it
  is a step-up (see "Compile breaks"), so a login method may carry that name.

  What 0.19.0 left expires by itself. To remove it at once, delete the rows
  that are not named by a key; in Valkey they are the keys `<prefix>:sess:*`
  whose last part has the 36 characters of an id.

  ```sql
  -- SQLite, PostgreSQL
  DELETE FROM sessions WHERE length(id) <> 64;
  -- MySQL, MariaDB
  DELETE FROM sessions WHERE CHAR_LENGTH(id) <> 64;
  ```

  The SQL stores read the binary column `data_bin` only. The text column
  `data` stays in the schema and is written empty, and a row whose `data_bin`
  is NULL is `SqlStoreError::Decode`, where 0.19.0 read the text column for
  such a row. A MySQL table created with `data TEXT` no longer needs `MODIFY
  data MEDIUMTEXT`; a table older than the binary column needs `ADD COLUMN
  data_bin LONGBLOB NULL` and nothing else.

  `SessionMetrics::session_row_refused` stays at zero through this upgrade,
  since no row of 0.19.0 is found; a count above zero means something beside
  this library writes rows to the session store. A rollback to 0.19.0 finds
  none of the sessions 0.20.0 stored.

- **A step-up no longer extends a session's absolute lifetime.** In
  0.19.0 a finished step-up moved `authn_time`, which the absolute age cap
  (`max_authenticated_age`, 7 days by default) counted from, so a session
  that stepped up now and then never reached it. The cap now counts from
  the login (`signed_in_at`), and so do a refresh token issued from the
  session and an impersonation begun on it. Recency checks still read the
  step-up's time.
  Nothing to change in code unless it read `authn_time` as the session's
  age (see "Compile breaks").

- **The session layer records each session it ends, before it ends it.**
  A session past an absolute age cap, one the registry no longer holds,
  one revoked or untracked while its id rotated and one whose rotation the
  store could not make were ended with a log line and no audit row. Each
  is now reported to the layer's audit sink first (`SessionExpired` for an age
  cap, `SessionInvalidated` for the rest, with the reason in `error`; *Audit
  events* has the table), and its row is removed only when the sink has
  answered. Three things follow for a deployment. While the audit store
  refuses the row, such a session is still refused on every request but
  stays in the session store, and the client keeps its cookie, until a
  request finds the audit store working; before, it was deleted at once.
  Several requests that carry one ended cookie at the same moment leave
  one row: the layer claims the session on its stored row first
  (`SessionData::ending`), and the requests that lose the claim run as
  guests without ending anything, so their responses do not replace the
  cookie; the one that wins does. And the claim is the decision: a
  request that finds one more than thirty seconds old finishes the ending
  for the reason the claim holds, so a claimed session is never served
  again. A request that was already running when the claim was made
  writes its changes onto the claimed row and leaves the claim in place;
  a rotation of the id is not carried out for a claimed session, and its
  changes are dropped with a warning in the log. The session validator's
  endings are recorded the same way (`SessionValidator::enforce`,
  `require_valid_session`, the validator form of `require_authn!`):
  `session_not_registered` where the layer had not ended the session
  already, or `session_tenant_not_confirmed` for the tenant check of
  `AuthnService::session_validator_with_identity_check`, each one
  `SessionInvalidated` row in the service's audit trail. A session the
  layer ends leaves the registry too, so it is no longer listed or counted
  and a socket that watches it is told.

- **On a Valkey cluster, `ValkeyDeviceStore` refuses a key prefix without
  a hash tag.** Every write of a device is one script over several keys,
  which a cluster runs only when they share a slot, so under such a
  prefix every write failed with the client's or the server's own error
  wrapped in `ValkeyDeviceStoreError::Connection`. `with_prefix` now
  panics there with a message that names the prefix and the remedy,
  `try_with_prefix` returns `ValkeyDeviceStoreError::PrefixWithoutHashTag`
  instead, and a store left on the default prefix (`axess`, which has no
  hash tag) answers every write with the same error. The health check of
  such a store reports `Unhealthy` with that error's text without asking
  the server, where it used to report `Healthy` whenever a `PING` was
  answered, so a readiness probe built on it now fails at start. Give the
  store a prefix with a hash tag, such as `{axess}`. A single node is
  unaffected.

- **A rotation the session store could not make leaves no row under the
  new id either.** The layer used to delete the old row and set the cookie of
  the new id, which no row was meant to back; a store that had written the new row
  before it reported its error left a live session behind that cookie. The
  layer now deletes both.

- **An authenticated request for which the device resolver finds no tenant
  is reported.** With no tenant, `LifecycleDeviceResolver` creates no
  device and issues no device cookie, so nothing can recognise that user's
  devices and a "known device" judgement has nothing to rest on. The
  default `tenant_fn` cannot produce this, because the session layer hands
  the resolver the tenant the session authenticated into; a `tenant_fn` of
  your own that answers `None` for an authenticated request can, and did
  so silently. Such a request is now a failed resolution
  (`LifecycleResolveError::TenantMissing`): the session keeps the device it
  has, where the silent answer took it away, the first such request writes
  one `error` line naming the fault, and the session layer logs each failed
  resolution at `warn`. If you see it, make `tenant_fn` answer for every
  authenticated request, or remove it and rely on the default. A guest
  without a tenant is still silent.
- **An authenticated request the device resolver cannot fingerprint is
  resolved by what it presents.** A request with no `User-Agent` yields no
  fingerprint from the default extractor, and `LifecycleDeviceResolver`
  answered it with no device: the session lost the device it was bound to,
  a request that presented the device token or proved the device's key
  proved no device, and the next request without the device cookie created
  another. The fingerprint has no part in finding a device, so such a
  request is now resolved as any other, by its device token, its key or its
  session's device, and only no device is created for it. One that finds
  no device has none, and the first writes one `warn` line. A guest's
  request without a fingerprint still has no device, whatever it presents,
  and is not reported.
- **The device cookie holds one entry per device of a browser profile.** A
  profile that several accounts sign in on kept one device cookie, so each
  account switch overwrote it and minted a new `Unknown` device, and trust
  earned on the previous one was lost. The cookie's value now holds up to
  eight `<id>.<token>` entries joined by `~`, and a request is resolved to
  the first that proves a device its user may use. A value of one entry,
  as earlier releases wrote, reads as before; nothing needs to change. Before
  sign-in a profile whose cookie proves several devices is recognised as
  none, since nothing says which account is signing in.
- **A device row that holds a key cannot be read by 0.19.0.** A 0.19.0 node
  does not decode a device's bindings once they hold `DeviceBinding::Key`. No
  such row exists until you give the session layer a key service (see
  "Added"), so upgrade every node to this release before any layer is given one.
  Before a rollback after keys exist, set the policy to `Off` and call
  `DeviceKeyService::forget_device_key` for the devices that hold one. The
  sessions are not carried back either way: a rollback finds none of the
  sessions 0.20.0 stored.
- **A session's device holds for the person it was resolved for.** In 0.19.0
  a device resolved on a request stayed on the session, with the request's
  proof of it, when another person signed in on that session within the same
  request, until the next request resolved again. Now a handler that signs a
  second person in on a session another person was signed in on, and then
  reads `AuthSession::device_id`, `AuthSession::proven_device` or
  `AuthSession::user_device` in the same request, gets `None`, and the row is
  written without the device. The next request resolves the device for the
  new person. A person who begins a new login on their own session keeps
  their device for it. `AuthSession::data` and `AuthSession::with_data` still
  show the row as the request holds it. Nothing to change unless a handler
  read the device after a second sign-in on one request.
- **A user or tenant identifier holding a character that is drawn as nothing,
  or that reorders what is drawn, no longer signs in.** `User::validate`,
  `Tenant::validate` and `is_acceptable_identifier` refuse every character
  that `axess_identity::log_text::escapes` names: a control character; U+2028
  or U+2029; a bidirectional control (U+061C, U+200E to U+200F, U+202A to
  U+202E, U+2066 to U+2069); a zero-width character (U+200B to U+200D,
  U+2060); U+FEFF; a Hangul filler (U+115F to U+1160, U+3164, U+FFA0). Of
  these, the `is_acceptable_identifier` of 0.19.0 passed U+2028, U+2029, the
  zero-width non-joiner and joiner (U+200C, U+200D) and the Hangul fillers.
  The rule applies where an identifier is created (signup, `User::new`,
  `Tenant::new`, tenant provisioning) and where a stored row is read back:
  sign-in and password reset answer such a user as unknown, and refuse every
  login to such a tenant. Before upgrading, find these rows: load every user
  and tenant row and call `validate()` (an `Err` names a row the rule
  refuses), or test each identifier's characters with
  `axess_identity::log_text::escapes`, or match the column against the code
  points above. Rename what you find. A new identifier holding a zero-width
  joiner or non-joiner is refused too.
- **`verify_dpop_proof` refuses a proof whose header carries `crit`.** No
  critical extension is understood, so a proof that marks one as required is
  not accepted (RFC 7515 section 4.1.11). A client that sent `crit` in a
  DPoP proof, which RFC 9449 does not ask for, is refused where 0.19.0
  ignored the member.

- **A seeded generator yields another ES256 key.**
  `LocalIdpSigningKey::generate_es256_with_rng` draws the key through
  `p256` 0.14, which reads the generator in another order than 0.13 did.
  The same seeded `SecureRng` still gives the same key on every run, but
  not the key 0.19.0 gave for that seed. Who notices: a test that pinned
  the key id or the public coordinates of a key generated from a seed;
  record the new value. Keys loaded from PEM or DER, RSA keys and DPoP
  keys (`DpopKey::generate`, `DpopKey::from_seed`) are unchanged.

- **`AuthzStore::for_user_id` and `for_user_in_tenant` refuse a session
  without a context on policies that read `context`.** On an empty context
  a `forbid` that guards an optional attribute with `context has ..` stopped
  applying and the `permit` beside it allowed, so a rule such as "forbid
  unless MFA" was off for every handler that began its session without a
  context. These forms now answer `AuthzError::ContextRequired` when the
  policies in force read `context`; `NoContext` handed to a with-context
  form is refused the same way; and a session that is still held when a
  policy reload brings a read of `context` in is denied from then on
  (decision reason `context_required`). Before:

  ```rust,ignore
  let authz = state.authz.for_user_id(&user_id)?;
  authz.require("ViewDocument", &doc_id).await?;
  ```

  After:

  ```rust,ignore
  // The MFA fact comes from the authenticated session, never from the request.
  let ctx = StandardRequestContext::new(mfa_verified, client_ip.get());
  let authz = state.authz.for_user_id_with_context(&user_id, ctx)?;
  authz.require("ViewDocument", &doc_id).await?;
  ```

  The tenant form is `AuthzStore::for_user_in_tenant_with_context`, and
  `AuthzStore::for_session` reads user and tenant from the session. The
  question is asked of the policy set, not of the action: if any policy or
  template reads `context`, every session on that store needs one, the
  routes whose own rules read nothing included. A store whose policies read
  no `context` keeps `for_user_id` and `for_user_in_tenant` as they are. To
  find the call sites: every `for_user_id(` and `for_user_in_tenant(` on a
  store for which `PolicyStore::mentions_context` answers true.

- **A `FactorStore` of your own is held to the contract of its swap.** No
  signature changed, but run
  `testing::store_contract::assert_compare_and_save_factor_contract(Arc::new(store), &tenant, &user)`
  in its tests, under
  `#[tokio::test(flavor = "multi_thread", worker_threads = 4)]`, against the
  store opened as
  production opens it (the same database file, journal mode and pool size;
  a pool of one connection cannot race itself). The check overwrites the
  TOTP, HOTP and recovery-code rows of `user`, so give it a user made for
  the test. A swap that loses a race answers `Ok(false)`, never an error: a
  store that reads the row and then writes it in a deferred SQLite
  transaction fails the check; write the swap as one guarded `UPDATE`. A swap
  that compares stored text (`UPDATE ... WHERE config = <text of prior>`)
  never matches a row written before a field with a default existed, and
  its codes read as replays: add a version column that every write of the
  configuration moves, read id, version and configuration, compare the
  configuration as a `FactorConfig` value with `prior`, and write with
  `UPDATE ... WHERE id = ? AND version = ?`. Where the store has a flag
  that takes a factor out of use and its loads skip such rows, put the flag
  in the guard as well (`... AND version = ? AND enabled = 1`): a flag that
  does not move the version is not covered by the version guard. The
  SQLite example (`examples/sqlite/src/models/backend/factors.rs` and its
  migration `20261115000000_factor_config_version.sql`) shows each step.

- **`Fido2Provider::on_credential_used` receives the device the request
  proved.** An override is handed the device the request proved, by the
  device token or the device key, and is not called when the request
  proved none: a request that presented only the session cookie, a layer
  without a device resolver, or a build without the `device` feature. Code
  that recorded every ceremony against the session's device records only
  proven ones; a ceremony without a proven device is not a device's use of
  the credential.

- **A session with nobody signed in loses its device on a request that
  resolves none.** A `DeviceResolver` that fails, or a layer without one,
  leaves a signed-in session's `device_id` as it was, and clears it on a
  session with nobody signed in, so a device stored during one person's
  login cannot pass to another person whose login completes on that
  request. A session row merged with a concurrent write answers
  `AuthSession::proven_device` and `AuthSession::key_bound` only for what
  this request proved, and a rotation that changes the authentication state
  does not carry a device a concurrent request stamped on the retired row.

- **Events archived with rkyv are larger.** The archived `EventSubject` is
  36 bytes where it was 20, and an `Option` of it 40 where it was 24, so an
  archived `Event` is 32 bytes larger and the fields behind its `subject`
  have moved. An archive written by 0.19.0 cannot be accessed with the
  types of 0.20.0. Read it with 0.19.0's types; to carry it over,
  deserialise it there, write it as JSON and read that with 0.20.0. An
  `AuthEvent` archived with rkyv by 0.19.0 is likewise read with 0.19.0's
  types.

- **CSRF tokens, key registration offers and OAuth claim locks are bound to
  the session's key.** A CSRF token issued before the upgrade is void with
  its session.

- **The audit column `session_id` receives 64 hexadecimal characters.**
  Widen a column typed for a UUID (`UUID`, `CHAR(36)`). Rows written before
  the upgrade keep their value; an `AuthEvent` read from such a row carries
  the key of that id (`AuthEvent::session_id`). No session spans the
  upgrade, so no join across it is lost. A consumer that joined audit rows
  to sessions by id joins on the same column, whose value is now the name
  the session table, the registry and the logs use; a log line's
  `session_id` field is its first eight characters.

- **The audit archive drain finishes before the upgrade.** A batch that
  0.19.0 wrote to the archive and had not yet marked in its source is
  selected again after the upgrade and appended a second time, with
  `session_id` in the new form, because the archive's batch marker digests
  the serialised lines. On 0.19.0, stop the task `AuditRetentionLoop::spawn`
  started and call `AuditRetentionLoop::drain` by hand until it has nothing
  left to do. It has finished when `drain` returns `Ok` with
  `RetentionTickReport::archived` equal to 0: no row that is due is left
  unmarked (the count form of what
  `AuditRetentionSource::select_unarchived_before` selects gives 0). Then
  upgrade.

- **The sid store keeps its records under new names, and federated sign-in
  needs it.** `ValkeySidStore` writes `{<prefix>}:v2:...`, the whole prefix
  in one hash tag, so on a cluster it needs no hash tag in its prefix any
  more; a prefix that is empty or begins with `}` is refused by every call.
  What 0.19.0 left in the sid store expires by itself: sid mappings within
  25 hours, subject records within 30 days. To remove them at once, delete
  `<prefix>:sid:*`, `<prefix>:sub:*` and `<prefix>:ses:*` of the sid store's
  prefix; do not delete `<prefix>:jti:*`, the replay log's keys, which are
  unchanged. `RequestAuthnService::complete_oauth_login` answers
  `AuthnError::NoFlow` when the sid store cannot write the login's records,
  as it does when the registry cannot register the session: an outage of
  the sid store is an outage of federated sign-in, so make it as available
  as the session registry. A logout token an identity provider sends during
  an overlap is spent by whichever node receives it, and one a 0.19.0 node
  spent ends no session of 0.20.0.

- **A kick and a logout an identity provider sends find a session by a
  key it held before a rotation.** `RequestAuthnService::invalidate_session`
  ends the session a key from `AuthnService::active_sessions` leads to, even
  after that session rotated (a step-up, `rotate_session`, `regenerate`),
  where 0.19.0 answered `AuthnError::NoFlow`, so a list read a moment
  earlier stays usable. Its `SessionInvalidated` row names the key the
  session was under when it ended, which after a rotation is not the key
  you passed. A back-channel logout, by `sid` or by `sub`, and a
  front-channel logout ask the registry which key the session is under
  now (`SessionRevoker::current_key`) before they end it: they end a
  session that rotated after its OAuth login, where 0.19.0 ended nothing
  and answered the provider as if it had. For a session that had ended
  already a back-channel logout writes no `SessionInvalidated` row, and a
  token that ended nothing is counted by
  `SessionMetrics::back_channel_logout_unmatched`. Nothing changes in code,
  except in a `SessionRevoker` of your own (the `SessionRegistry` entry
  under "Compile breaks").

- **A rotation moves the registry entry in one step, and the layer makes
  the move.** `RequestAuthnService::rotate_session` behind a session layer
  built with a registry no longer signs the user out: the key rotates, the
  method writes nothing to the registry, and the layer moves the entry
  after the session's row has moved. A rotated session keeps its place in
  the oldest-first order the session limit evicts by, and a rotation
  publishes nothing on the old key's revocation channel. The layer moves an
  entry from the key it loaded, the key the service registered or the key
  the request arrived with: a handler of your own that registers a session
  itself (`SessionRegistry::register`) registers the key the session
  carries when the response is written (after the sign-in and any
  `regenerate`), or the key the request arrived with; an entry registered
  under a key in between is not moved, and the session is ended. A layer
  built with `SessionLayer::without_registry_insecure` still relies on
  `rotate_session` to move the entry, which it now does in one call.
  `UnknownLiveness::Accept` no longer keeps a session whose rotation the
  registry could not record: it is ended at once as `session_not_tracked`,
  where it was ended one request later as `session_not_registered`.

- **A password over `MAX_PASSWORD_BYTES` costs a known user and an unknown
  one alike.** The stored-hash path refused such a password before Argon2
  ran, while a refusal with no stored hash (an unknown identifier, a
  throttled or locked account) ran Argon2 on it against the dummy hash, so
  the work of a login with an over-length password told the two apart. The
  dummy check now refuses it the same way, in the same executor job: the
  answer is the same wrong-password answer it was, and no Argon2 runs on
  either path. `burn_password_check` spends no Argon2 on such a password
  either.

### Changed defaults

- **A tenant OAuth record is stored only with a proof that the tenant owns
  its client.** In 0.19.0 the first record to register an
  `(issuer, client_id)` pair held it, whoever wrote it. The directory's
  constructors now take `OwnershipProofs`, and every write asks them first.
  A deployment whose tenants register confidential clients names the
  probe, and the attestation for the public ones:

  ```rust,ignore
  let ownership =
      OwnershipProofs::accept(TokenEndpointProbe::new()).or_accept(OperatorAttestation);
  let tenants = StoredTenantOAuthProviders::new(store, cipher, ownership);
  ```

  A deployment where only operators write records, which vouch for every
  client they enter, names `OwnershipProofs::accept(OperatorAttestation)`
  and writes through `upsert_attested`. Records already stored keep serving;
  the proof is asked at their next write. Run
  `tenants.reprove(&tenant, &name)` over every stored pair once the
  directory names its proofs: it runs them against the record as stored and
  writes nothing, and each pair it refuses (`Reproved::Refused`) is a record
  to confirm with its tenant, and a squat to hand to its owner with
  `reassign_tenant_oauth_pair_as` or remove. The attesting operator is a
  deployment operator, an active user the identity store places in
  `TenantId::SYSTEM`: `attest_tenant_oauth_client_as` and
  `reassign_tenant_oauth_pair_as` refuse a user of any other tenant
  (`NotADeploymentOperator`), an operator whose account is not active
  (`OperatorNotActive`), the reserved `UserId::SYSTEM`
  (`OperatorIsSystemUser`), and one the identity store does not know,
  each by name. Create the operators who attest in `TenantId::SYSTEM`, and
  call both methods as a named one of them. Tests take
  `axess_core::testing::oauth_tenant::ownership_assumed()`, under the
  `testing` feature only.

- **`SocialProvider::new` and `OutboundOAuthClient::new` screen their
  egress.** Both name `EgressPolicy::screened()`, as
  `OAuthProviderConfig::discover` does: an endpoint whose host is a
  loopback, private, link-local, unique-local, shared-address or metadata
  address, `localhost` included, is refused at construction
  (`SocialError::Config`, `OAuthClientError::EgressRefused`, naming the
  setting and the range), a host name that resolves to one is refused when
  the request is made, and no request follows a proxy from the environment.
  In 0.19.0 both reached any address and followed `HTTPS_PROXY`. A token
  endpoint on the deployment's own network goes through `new_screened`
  with `EgressPolicy::unscreened()`, which keeps the 0.19.0 behaviour; a
  mock on loopback in tests through `new_screened` with
  `EgressPolicy::screened_allowing_loopback_http()`. A deployment that
  reaches its identity provider through an egress proxy names
  `unscreened()` and filters at the proxy.

- **A passkey change needs an authentication from the last five minutes.**
  `Fido2Options::default()` and `SecurityProfile::Standard` set
  `max_authn_age` to `DEFAULT_FIDO2_MAX_AUTHN_AGE` (five minutes) where
  they set no limit before. Beginning or finishing a passkey registration
  and deleting a passkey from a session that authenticated longer ago are
  refused with `AuthnError::NoFlow` and a failed `FactorSetup`,
  `FactorEnabled` or `FactorDisabled` audit row naming `authn_too_old`; the
  session steps up first (`begin_step_up`) and then changes the credential.
  A signup session enrolling its first passkey carries no authentication
  time and is not affected. The opt-out is explicit:

  ```rust,ignore
  AuthnService::builder(identity, factors).with_fido2_options(Fido2Options {
      max_authn_age: None, // no recency requirement for passkey changes
      ..Fido2Options::default()
  })
  ```

  A deployment that wants another window sets `Some(duration)` the same
  way. A service built under a security profile is held to the profile's
  five minutes (see "A service built under a security profile is held to
  it" under "Behaviour changes"): there the opt-out, or a longer window, is
  written on the builder and named with the waiver, and a `None` assigned
  on the profile's values leaves the limit in force. A shorter window needs
  no waiver, before the profile or after it.

  ```rust,ignore
  let authn = SecurityProfile::Strict
      .values()
      .authn_service_builder(AuthnService::builder(identity, factors))
      // No recency requirement for passkey changes, and it says so.
      .with_fido2_options(Fido2Options { max_authn_age: None, ..Fido2Options::default() })
      .waive_profile_floor(ProfileSetting::Fido2MaxAuthnAge)
      .build();
  ```

- **When the service hashes at a cost other than the pinned default, every
  refusal on the password form spends a run at that cost and one at the
  previous cost.** In 0.19.0 a wrong password against a hash made under an
  earlier cost was checked at that cost alone, so a dormant account whose
  hash predates the cost change answered in different work from an unknown
  identifier. A service with a previous cost now spends the same on every
  refusal: one run at the current cost and one at the previous cost, each
  its own executor job, whether the identifier is unknown, the password is
  wrong against a current or a previous hash, the guess is throttled, the
  account locked, or the account closed between the lookup and the
  password. A right password against a previous hash spends the same on
  its check and its rehash.
  The previous cost is new, `AuthnServiceBuilder::with_previous_argon2_cost`,
  and defaults to the pinned `Argon2Cost::default()` whenever the service
  hashes at another cost (`with_argon2_cost`, or a security profile such as
  `Strict`), and to none while it hashes at the pinned cost, so a
  deployment on the defaults sees no change. A deployment that raised the
  cost spends one more Argon2 run per refusal. Name the earlier cost when
  the hashes came from another one; when every stored hash is current
  (the cost was raised before the first user signed up), opt out:

  ```rust,ignore
  AuthnService::builder(identity, factors)
      .with_argon2_cost(cost)
      // Every stored hash is at `cost`: a refusal spends one run.
      .without_previous_argon2_cost()
  ```

  A hash under a cost that is neither the current nor the previous one
  still costs its own check on top, and the service logs that once at
  `warn`, naming `with_previous_argon2_cost`.

- **`OAuthProviderConfig::discover` and `discover_with_private_key_jwt`
  refuse an issuer, an advertised endpoint or a `jwks_uri` on a reserved
  address, and a plain-HTTP issuer on loopback, with `OAuthError::Config`
  naming the setting and the range.** Both ran under
  `EgressPolicy::unscreened()`, which checked the transport rule alone,
  while the OIDC primitives and the tenant provider store were screened by
  default. They now run under the default, `EgressPolicy::screened()`. A
  deployment whose identity provider is on its own network names the
  opt-out it already had for tenant providers: `discover_screened` (or
  `discover_screened_with_private_key_jwt`) with `EgressPolicy::unscreened()`.
  Local development against a mock on `http://localhost` or `http://127.0.0.1`
  names `EgressPolicy::screened_allowing_loopback_http()` the same way; the
  two examples do.

- **`SecurityProfile::Standard` screens egress.** The standard profile
  restates the library's defaults as values, and its `egress_screened` was
  still `false` after discovery began to screen by default (the entry
  above), so `SecurityProfile::Standard.values().egress_policy()` handed the
  discovery entry points a looser policy than they use when none is named.
  It is `true` now, under both profiles, and `egress_policy()` returns
  `EgressPolicy::screened()`. A deployment that passed the standard
  profile's policy to `discover_screened` to reach an identity provider on
  its own network assigns `egress_screened = false` on the values before
  calling `egress_policy()`, or names `EgressPolicy::unscreened()`.

- **A tenant OAuth credential under the earlier binding is refused at
  use; the directory moves every stored one when it starts.**
  0.20.0 seals a tenant OAuth credential to every field that decides where
  and how it is presented, which 0.19.0's binding (the issuer and client id
  only) did not. `FactorSecretCipher::with_earlier_tenant_binding` names
  what happens to a credential still sealed the 0.19.0 way, and defaults
  to `LegacyBlobs::Reject`: refused at use. The directory moves every
  stored one first, once. Start it with `started()`:

  ```rust,ignore
  let tenants = StoredTenantOAuthProviders::new(store, cipher, ownership)
      .started() // moves every earlier-binding credential, or names the one it cannot open
      .await?;
  ```

  The pass lists every record (`list_all`), re-seals each credential due a
  re-seal with one `put_if_revision`, logs how many it moved and how many
  the store could not write at `info`, returns both as a `ResealReport`,
  and moves none the second time. A credential that opens under no binding the
  cipher knows (another key, a row damaged in the store) stops the start
  with `OAuthError::Store` naming the tenant and the provider; fix or
  remove that record. A directory built without `started()` runs the same
  pass before its first resolution and resolves nothing until it
  succeeds, so code that upgrades without the call moves the stored
  credentials too, and a record the pass cannot move refuses every
  resolution with that error instead of stopping the start. A record
  written in the earlier binding after the pass ran (by a 0.19.0 node), or
  one the store could not move, is refused at use, with the cipher's
  `FactorSecretError::Open` as before and a `warn` line naming it and the
  earlier binding as the reason. During a rolling upgrade in which 0.19.0
  nodes still write records, opt in to reading them until the last such
  node is gone:

  ```rust,ignore
  FactorSecretCipher::new(key)
      // 0.19.0 nodes still write: read their records, re-sealed on first use.
      .with_earlier_tenant_binding(LegacyBlobs::Accept)
  ```

  `LegacyBlobs::AcceptUntil(cutoff)` bounds that window.

- **An event sealed under the first AAD tag is refused unless the reader
  names the opt-in.** `FirstTag` defaults to `Reject`, where the reader of
  0.19.0 tried the first tag after the second with no end date. The first
  tag bound only the id, kind, tenant and subject of an event, so whoever
  could write the event store could rewrite the status, the actor or the
  time of an event sealed under it and the payload still opened; a reader
  that accepts the tag accepts that, and now has to say so:
  `open_aads_for(&event, FirstTag::Accept, now)`, or
  `FirstTag::AcceptUntil(cutoff)` with the instant the acceptance ends, read
  on the reader's clock. Only events sealed by a release before 0.18.0, or
  by a seal path that still called the removed `envelope_aad`, carry the
  first tag.

  `axess-events` computes associated data and holds neither a key nor a
  store, so it cannot re-seal those events itself, as the directory does
  for tenant OAuth credentials. The process that holds the key runs the
  pass once, before its readers move to the default:

  ```rust,ignore
  for mut event in store.encrypted_events().await? {
      let aads = open_aads_for(&event, FirstTag::Accept, now)
          .expect("an encrypted body");
      // The first value is the second tag's: an event that opens under it
      // needs nothing.
      if open(&key, &event, &aads[0]).is_ok() {
          continue;
      }
      // Sealed under the first tag: seal the plaintext again under the
      // second, with a fresh nonce, and write the event back.
      let plaintext = open(&key, &event, &aads[1])?;
      let aad = envelope_aad_for(&event).expect("an encrypted body");
      seal(&key, &mut event, &plaintext, &aad)?;
      store.replace(&event).await?;
  }
  ```

  `store`, `open` and `seal` are yours: the event store and the AEAD your
  seal path already uses. An event that opens under neither value is damaged or
  sealed under another key, and the pass does not fix it. The re-seal binds
  the fields as the store holds them at that moment: it cannot show that a
  status, an actor or a time is the one originally written, only stop them
  changing unnoticed from then on. Events past retention need no pass.
  During a rolling upgrade in which writers of an earlier release still
  seal under the first tag, readers name `AcceptUntil` with the end of that
  window, and the pass runs after the last such writer is gone.

- **`axess_testing::stall`'s gate waits ten seconds at most.**
  `Gate::wait`, `Gate::until_entered` and `abort_inside` waited without
  end, so a change that kept the code under test from reaching the gated
  call hung the test run. Each now fails the test with a message after
  `Gate::DEFAULT_BOUND` (ten seconds). A test whose gated caller takes
  longer to arrive, or that opens the gate later than that, builds the gate
  with `Gate::with_bound(duration)`.

- **Device-bound sessions**, behind the new `device-keys` feature (off by
  default; it needs `jwt-aws-lc` or `jwt-rust-crypto` beside it). A client
  registers a P-256 key whose private half it cannot export, the device row
  keeps the public half (`DeviceBinding::Key`), and from then on a session
  bound to the key is served, and the device counted as proven, only for a
  request that carries a short-lived proof cookie minted against a
  signature by that key over a challenge the server chose. A copied cookie
  store is then worth the rest of one proof cookie's life (10 minutes and
  30 seconds by default) in place of the session's. Wiring:

  ```rust,ignore
  let keys = DeviceKeyService::new(devices.clone(), DeviceKeyConfig::new("https://app.example"))?;
  let app = Router::new()
      .merge(routes)
      .merge(keys.router())
      .layer(
          SessionLayer::new(store, signing_key, registry, audit)
              .with_device_resolver(resolver)
              .with_device_keys(keys.clone()),
      );

  // Where refresh tokens are redeemed: the device store and the key service.
  let (session, rotated) = Refresh::new(&plaintext, &tenant, status_check)
      .device_store(&devices)
      .device_key(&keys, proof)
      .run(&refresh_store, &config, &rng, now)
      .await?;
  ```

  Merge `keys.router()` inside the session layer, which answers the two
  key paths. The browser posts to them itself, with no form token: the
  session layer marks a `POST` to either path, and a `CsrfLayer` between
  the two lets a marked request through. The layer needs the device
  resolver: keys are registered on, and sessions bound to, the device it
  proves, and a layer given a key service and no resolver logs an error
  when it is built. The SQLite example built with `--features device-keys`
  wires all of it where a person signs in
  (`examples/sqlite/src/web/device_keys.rs`).

  Give the key service to every session layer that shares the session
  store, and to every refresh. A layer that was given none, and a build
  without the feature, cannot check a key: it runs a request whose session
  is bound as a guest, leaves the row for a layer that can check it, and
  logs the first such request at `error`. A refresh given the device store
  and not the key service refuses the token of a keyed device
  (`RefreshError::KeyCheckMissing`); one given the key service holds that
  token to a proof by the key, and a token presented without one has its
  family revoked.

  Start on `KeyBindingPolicy::Prefer`, the default: a client that registers
  no key keeps a bearer session and a device proven by its token, and every
  session and device that does have a key is held to it.
  `KeyBindingPolicy::Require` ends a signed-in session (in a step-up too)
  that is still not bound two minutes after its login, which signs out
  every browser without support; the ending is recorded through the
  `SessionEndAudit` the layer is built with, as `key_binding_required`
  (`SessionEndReason::KeyBindingRequired`; with
  `AuthnService::session_end_audit` a `SessionInvalidated` row). Read the
  share of sign-ins that end up bound before you choose it.
  `KeyBindingPolicy::Off` is the switch for a fault in a browser's
  implementation, and the one way to serve bound sessions as bearer
  sessions: it offers no key, answers neither path and proves every device
  by its token. A device-store outage longer than a proof cookie's life
  signs bound sessions out until the store is back: that is the price of
  not serving them without proof. The browser front-end's wire details were
  compared with the W3C editor's draft of 9 November 2026, and no real
  browser has run against it: it reads the browser's two request headers
  quoted or bare, answers a final refusal at the refresh path with 400 (a
  403 there tells a browser to sign again), and marks the answers of the two
  paths as not embeddable. The design, what it answers and what it does not
  are in
  [Design: device-bound sessions](../../sessions/device-bound-sessions.md).

### Decisions left as they are

- **An `(issuer, client_id)` pair goes to the record that registers it
  first.** The unique index keeps the pair to one record, and the record is
  stored only with a proof that the tenant owns the client (under "Changed
  defaults"); `with_global_registration`
  reserves the global providers' pairs only, on the directory it is called
  on. An operator hands a squatted pair to its owner with
  `reassign_tenant_oauth_pair_as`, under "Added".

  device check does not depend on it, since it reads through `load_fresh`;
  a cached `load` still does.
